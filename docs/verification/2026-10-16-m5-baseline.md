The owner ran `caffeinate -dis python3 tools/benchmark_scenes.py` on the M5
MacBook Pro (Apple M5, 10 CPU cores, 16 GB, macOS 27.0.1). It measured commit
`903884e` with a clean tree, which includes the entity-fixture and
simulation-distance fixes from the previous run. Every executable fingerprint
matched the runner.

Configuration (all 15 runs):

- 1920 × 1080 physical pixels in a window on the built-in 3024 × 1964 display.
- Enhanced graphics, view distance 256 blocks (rd 8), simulation distance
  160 blocks, seed 12345.
- Present mode requested `AutoNoVsync`, resolved `Immediate`.
- 10 s warm-up and 60 s samples; streaming samples for 180 s.

## Result

**All 15 runs are valid, so this is the M0 reference baseline (PERF-01).
The 240 FPS gate still fails** in streaming and in one survival run.

Every run completed exactly 20 ticks per second, with no pause time and no
unpresented frames. The entity scene held its 160 fixture mobs (one run ended
at 159, inside the tolerance).

## Findings

- **Streaming stalls are periodic and tied to distance travelled.** Each
  180 s run has 451–453 frames over 50 ms (worst 123–150 ms), in 53–54 bursts
  of about 8.5 consecutive slow frames. There are none for the first 44–47 s.
  After that, a burst comes every 2.67 s (median, identical in all three
  runs). At the route's 12 blocks/s that is exactly 32 blocks, two Java chunks
  or one storage chunk. Some per-chunk-row step on the main thread (chunk
  insertion, lighting, mesh uploads or generation-herd population) runs once
  the camera leaves the preloaded area. Entities grow from about 290 to 750
  over the route. This is deterministic, so it can be profiled directly.
- **The survival failure is display pacing, not slow frames.** Survival run 1
  had 638 frames at exactly 8.33 ms, in stretches of up to 92 consecutive
  frames, all between 5 s and 25 s into the sample. Its other two runs pass.
  Streaming runs 2 and 3 show the same episodes (176 and 857 frames), which
  push their p99 from 4.3 ms to over 8 ms. The previous run had them in a
  different survival run. They are intermittent, appear in runs of
  consecutive frames, and land on whichever scene is running, which suggests
  the built-in display or window server sometimes paces presentation at
  120 Hz despite `Immediate`. Without those episodes, survival's typical
  frame times match the other scenes.
- **The steady-state scenes otherwise pass.** Building, entities and
  automation pass every run. Their slowest frames are short isolated spikes
  (worst 9.6–21 ms), never over 50 ms.
- **Memory.** Peak RSS is 279–427 MB; the building scene uses the most.
  Long-session memory stability is a separate check this suite doesn't make.

## Open questions and decisions

- **Simulation distance.** §6.1 of the roadmap asks for Java's 8 chunks
  (128 blocks) in the comparison setup. The game runs 10 chunks (160 blocks)
  by default, and `benchmarks/scenes.json` now specifies the 160 blocks that
  actually ran. Either the benchmark should force 128 blocks (a harness change
  and a re-run) or §6.1 should say 160. This is the owner's call.
- **120 Hz episodes.** Presentation is uncapped in this baseline, so the
  earlier question of measuring 240 FPS against a 120 Hz display reduces to
  whether runs with 8.33 ms episodes count. Repeating them with the window on
  an external display would show whether the built-in panel causes them.
- **Streaming budget.** §6 asks M0 for explicit streaming and hitch budgets
  before streaming can be Verified. None is set yet.
