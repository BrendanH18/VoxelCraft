Reference facts:

- Four stages × waxed/unwaxed × four horizontal facings × four poses × dry/wet
  = 256 states. Default facing north, standing, dry. Placement faces opposite
  the player's horizontal direction and waterlogs when the destination fluid
  is the source `Fluids.WATER` (not its flowing variant).
- Pose declaration order / serialized name / comparator output:
  `0 standing 1`, `1 sitting 2`, `2 running 3`, `3 star 4`.
  Next pose wraps star to standing; out-of-range BY_ID resolves to standing.
- Every pose/facing uses `column(10, 0, 14)`: `[3,0,3]..[13,14,13]` in sixteenths,
  for collision and selection. No occlusion, zero emission. Dry light opacity
  zero; wet opacity one. Water pathfinding is allowed when waterlogged.
- Strength 3, blast resistance 6; pickaxe is the efficient tool, but correct
  tools are **not** required for drops and no tier is required. Piston reaction
  is POPPED. There is no floor-support requirement.
- Oxidation uses the common copper WeatherState enum: attempt probability
  `0.05688889`, younger unwaxed copper anywhere within Manhattan distance four
  vetoes; otherwise `((older+1)/(older+same+1))²`, multiplied by 0.75 for the
  unaffected stage. Waxed neighbors are ignored, terminal unwaxed stages count.
  Statue and other copper neighborhoods affect each other.
- Lightning resets a directly struck unwaxed statue to unaffected. A waxed
  strike retains wax/stage but still starts 3–5 cleaning walks, each 1–8 steps,
  with up to ten candidate cells per step in a 3³ neighborhood. Walks ignore
  waxed blocks and reduce unwaxed copper one stage. A cleaned statue does not
  automatically resurrect. All shared block properties carry across changes.
- Loot is one same-stage/wax block item, subject to survives-explosion, copying
  CUSTOM_NAME from the block entity and `copper_golem_pose` into BLOCK_STATE.
  Facing and waterlogging are not copied to the item. `Items` registers
  BLOCK_STATE with standing pose as the item default, so ordinal zero correctly
  represents both a default item and standing statue loot. Fortune/silk do not
  alter this. Pick-block's block-entity method also copies components and pose.
- Only four shapeless waxing recipes exist (one statue + one honeycomb → one
  waxed statue). They produce default components; the recipes do not copy the
  input's custom name or pose. There is no ordinary construction crafting recipe.
- `createStatue` copies CUSTOM_NAME, not a complete serialized mob. Reactivation
  creates a fresh triggered golem, restores name, centers X/Z on the block,
  uses the block's Y and facing for body/head/yaw, pitch zero, and plays its
  spawn sound. Pose/health/carried inventory/AI are not restored from a statue
  by `CopperGolemStatueBlockEntity`.

## Public API and parent integration contract

`world::copper_golem_statue` is independent of any CopperGolem entity module:

- `Statue { stage: copper::Stage, waxed, facing: block::Facing, pose, waterlogged }`;
  `decode(Block) -> Option<Statue>` and `block(Statue) -> Block`.
- `Statue::new(stage, waxed)` supplies Java default properties;
  `item_block(stage, waxed)` is the canonical block item.
- `Statue::cycle_pose()`, `wax() -> Option<Statue>`, `scrape() -> Option<Statue>`
  are pure and preserve every unrelated property. Scrape removes wax first,
  otherwise reduces oxidation once; None means unaffected/unwaxed.
- `Pose::{ALL, from_id, name, next, comparator_output}` and
  `comparator_output(Block) -> Option<u8>` expose the reference ordering.
- `Statue::item_stack(StackName)` preserves pose using **this item family's**
  existing `Stack.entity_data` payload (`0..=3`, ordinal; invalid reads default
  to standing), and custom name using `Stack.name`. No new Stack fields or
  standalone item IDs. `item_pose(Stack)` reads that pose for placement;
  `item_model(Stack)` supplies a pose-bearing block to Stack-aware renderers.

Parent-owned work required before ordinary interaction can be claimed. These
block callbacks are subject to the existing Java use dispatch: spectator skips
ordinary use; secondary-use with an item in either hand bypasses block use and
tries the held item directly. Both empty hands still enter the block callback
when secondary-use is active. Preserve that gate when wiring this table:

| Click/context | Required Java behavior |
| --- | --- |
| Unwaxed statue + honeycomb | Let honeycomb wax it, consume one outside creative; preserve pose/facing/water/name. Do not cycle pose. |
| Waxed statue + honeycomb | Cycle pose; base statue block consumes the interaction before honeycomb can act. |
| Any statue + non-axe item / ordinary empty-hand use | Cycle pose, play become-statue sound, issue block-change event and wake comparators. Preserve other properties and block entity. |
| Waxed statue + axe | Unwax only; normal axe wear/effect. |
| Unwaxed exposed/weathered/oxidized + axe | Scrape exactly one stage; normal axe wear/effect. |
| Unwaxed unaffected + axe | Attempt resurrection from the block entity, axe wear one. Java charges wear even if entity creation returns null; remove block only on success. |
| Place statue item | Choose facing from player (opposite), read `item_pose`, derive water from destination source, transfer `Stack.name` into world block entity. |
| Pick/drop | Call `item_stack` with the stored block-entity name, retain pose. Plain `picked_item` returns only Item and cannot carry components. |

Keep the persistent named block entity across **any** statue-to-statue change
(stage, wax, facing, pose, water), as Java's
`shouldChangedStateKeepBlockEntity` accepts the whole statue tag. Parent must
clear it only when the family is replaced/removed, and supply that stored name
to the loot/pick helper before removing the record. Current generic mining,
silk, explosion and piston drops preserve pose but have no named-world record
to consult until parent integration. Preserve water on removal/resurrection:
normal `World::set_block(..., AIR)` leaves a source for a wet statue; do not use
`edit_exact` there unless intentionally discarding water.

Inventory, first-person hand, dropped items, frames and shelves use
`item_model(stack)` to display the carried pose. Item-only previews show the
standing original statue model. Third-person entity held-item models belong to
the mob/model integration owner and still need component routing; sound/player
transaction routing is also left to the parent. Models/textures are original:
eight boxes, four visibly distinct poses, all facings, stage-specific riveted
copper/face/cap layers. Wax shares its stage's artwork, as in Java.
