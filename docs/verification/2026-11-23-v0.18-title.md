Status: **Implemented, unverified.** The owner approves the look before this

## What was built

### The wordmark

[`src/app/title/art.rs`](../../src/app/title/art.rs) draws an original
pixel-art wordmark in code: "VoxelCraft" in mixed case, each letter cell a
small bevelled cube (lit top and left edges, shaded right and bottom),
"Voxel" in moss greens and "Craft" in warm ambers, lighter towards the top,
with a dark rim and a soft two-pixel drop shadow. It is 254 x 39 pixels,
inside Java's 256 x 44 logo box, drawn at one GUI pixel per image pixel,
centred 30 GUI pixels down (`LogoRenderer.DEFAULT_HEIGHT_OFFSET`). It was
designed from scratch on a 5 x 7 cell grid; it doesn't trace Minecraft's
logo, its lettering or its stone texture, and it has no "Edition" line or
splash. The menu arrangement, the version in the bottom-left corner and the
updater's notice and button are unchanged.

### The UI image atlas

`render::ui` gains a 512 x 512 RGBA (sRGB) image atlas, bound beside the
font as `@group(2) @binding(1)` of the UI pipeline, and `Ui::image` draws a
part of it (UI layer `-3`). The wordmark sits in the top-left 256 x 64, the
default world icon beside it, and 56 world-icon cells of 64 x 64 below.
`Renderer::upload_ui_image` writes a region.

### The panorama

- **Faces.** Six 1024 x 1024 RGB PNGs in [`assets/panorama/`](../../assets/panorama/)
  (3.5 MB, embedded in the executable, a new `panorama` asset kind checked by
  `assets::validate` and `tools/validate_assets.py`): a savanna village with
  a pond and a river, seed 1234, from -942, 78, 190 at time 0.2, clear
  weather, render distance 8. They were **rendered by the game itself**:
  `--panorama DIR` (with `--screenshot`, a square `--size` and a `--pose`)
  renders each face as a square 90-degree view once the scene has settled,
  one a frame, and rewrites them as RGB PNGs. The up and down faces turn
  view space from a northward view, since the camera's Y-up view can't look
  straight up. How to regenerate them:
  [the title panorama](../development.md#the-title-panorama).
- **Drawing** ([`src/render/panorama.rs`](../../src/render/panorama.rs),
  [`panorama.wgsl`](../../src/render/shaders/panorama.wgsl)): a full-screen
  triangle; each pixel's direction picks a face (north, east, south, west,
  up, down, `panorama_0`..`5`, Java's order) in a six-layer texture array
  with linear filtering and a full mip chain built by averaging in linear
  light (Java: blurred sampling, `MipmapStrategy.MEAN`). It samples one
  fixed mip level per frame, so the cube's edges never show a derivative
  seam. Java's camera: 85-degree vertical field of view, tilted down 10
  degrees, spin `+= realtimeDeltaTicks x speed x 0.1` degrees wrapped to
  [-180, 180) (2 degrees a second at 100%). The spin is kept for the whole
  run, as Java's `Panorama` is, so going back to the title carries on.
- **Over the title menu** nothing is drawn on top: Java 26.3's
  `panorama_overlay.png` is a single transparent pixel (asset index 34), so
  the old 25% darkening is gone.
- **Under the screens opened from the title** (Select World, Create New
  World, Options, ...) the panorama is blurred by Menu Background Blur
  (Track 2's `menuBackgroundBlurriness`, 0 to 10, default 5; 0 leaves it
  sharp), as Java's `Screen.renderBlurredBackground` does: thirteen samples
  in a disc around each pixel, each from a mip level matching their
  spacing, drawn into a target a quarter of the window's width and height
  and stretched over it. Over it each screen draws Java's menu backdrop,
  black at 64 of 255: Java's off-world `menu_background.png` and in-world
  `inworld_menu_background.png` are the same (read from the 26.3 client), so
  the toolkit now draws Track 2's backdrop on and off the world.
- **Loading.** The title decodes the faces and builds their mips on a
  thread of its own when it first opens; until they are on the GPU the old
  turning sky shows. The texture stays for the rest of the run. Scripted
  captures wait for the faces and hold the spin at 0, so two builds
  compare.

### Panorama Scroll Speed

Accessibility Settings gains Java's **Panorama Scroll Speed** slider,
saved as `panoramaScrollSpeed` in `options.txt` (0..1, default 1.0,
labelled as a percentage with no OFF, e.g. "Panorama Scroll Speed: 100%").
It sits after Damage Tilt: the options between them in Java's order
(glint speed and strength, Hide Lightning Flashes, Monochrome Logo) aren't
in the game. 0% holds the panorama still. Old `options.txt` files load with
the default; out-of-range and non-numeric values are clamped or ignored.

### World icons

- **Capture** ([`src/app/world_icon.rs`](../../src/app/world_icon.rs),
  rule in [`voxelcraft::title::icon`](../../src/title.rs)): Java's
  `GameRenderer.tryTakeScreenshotIfNeeded`/`takeAutoScreenshot`. In a world
  this game hosts (not a LAN client), once a second: if the world folder
  already has a regular file `icon.png`, stop for this visit; otherwise,
  once more than ten 16-block sections are drawn (VoxelCraft counts 8 per
  32-block chunk mesh drawn last frame) and nothing is left to generate or
  mesh, take the frame. The renderer copies the centred square of the first
  view **before its HUD** (Java takes it after the level, before the GUI, so
  the hand shows and the HUD doesn't), reads it back without waiting for the
  GPU, and a thread shrinks it to 64 x 64 by averaging and writes an RGB PNG
  through `icon.png.tmp` renamed into place. One capture is in flight at a
  time; a failed one is tried again a second later. Nothing in `level.txt`
  or the world's data changes, and loading the world never waits for it.
  Scripted runs take no icon unless `--world-icon` asks (the capture tool
  uses it).
- **Showing them** ([`select.rs`](../../src/app/title/select.rs)): each row
  draws its world's icon at 32 x 32 GUI pixels, with Java's `0xA0909090`
  hover wash and play arrow. Icons are read lazily as rows are drawn, at
  most four files a frame, into atlas cells reused round-robin; the list
  forgets them when it is rebuilt, so a new or reset icon shows. Before
  reading, Java's checks: a regular file, not a symbolic link; and a 1 MiB
  cap of VoxelCraft's own. The PNG must decode and be 64 x 64 (Java's
  `FaviconTexture.upload`). A missing file, an old save from before icons,
  a corrupt, truncated or wrong-sized PNG, a folder or a link all fall back
  to the **default icon**: an original muted pixel landscape (sky, a hill,
  grass over earth), not Java's `unknown_server.png`.
- **Reset Icon** ([`edit.rs`](../../src/app/title/edit.rs)): Edit World's
  first button under the name field, as in Java. It is greyed out when the
  world has no `icon.png`; pressing it deletes the file (quietly, like
  `FileUtils.deleteQuietly`) and greys itself out, and the next visit takes a
  new icon. In the smallest windows (320 x 180 GUI pixels) Reset Icon and
  Make Backup share a row so the column fits.
- **Empty list**: when the list shows no rows, it says why and what to do:
  "No worlds yet / Choose Create New World to make one.", or "No worlds
  match "…" / Clear the search to see all N worlds." Java shows nothing
  (and opens Create New World instead when there are no worlds, which
  VoxelCraft still does from the title menu).

### Monochrome Logo (assessed, not added)

Java's Monochrome Logo (`darkMojangStudiosBackground`, "Changes the Mojang
Studios loading screen background color to black.") recolours the resource
loading overlay. VoxelCraft has no branded loading screen: the window opens
on the title, and worlds stream in behind the HUD. The option would change
nothing, so it isn't added; it stays listed as left out in Accessibility
Settings' module notes.

## Measurements

All on a Boat `large` sandbox (x86-64, 8 vCPU) with Mesa's software Vulkan
under Xvfb: **relative only**, never the frame-time gate, which is the
owner's run on the reference Mac.

- **Title scene** (`--benchmark-scene title --benchmark-offscreen`, 1920 x
  1080, 5 s warm-up, 20 s sampled, cycling the title menu and every screen
  over it), the starting commit against this branch, alternating, two
  rounds each:

  | Build | p50 ms | p95 ms | p99 ms | 1% low FPS |
  | --- | --- | --- | --- | --- |
  | before (sky) | 4.95 / 5.16 | 6.10 / 6.28 | 6.68 / 7.05 | 140 / 127 |
  | after (panorama) | 6.53 / 7.45 | 8.23 / 10.12 | 9.64 / 11.59 | 94 / 81 |

  The software renderer pays per texel sampled: the title menu takes one
  sample a pixel, the blurred screens thirteen a pixel at a sixteenth of
  the pixels plus one to stretch it. Drawing the blur at full size first
  cost p50 41 ms there, which is why it is drawn small. The UI geometry
  changes little (the wordmark is one quad instead of ten scaled strings).
  The title scene is in the offscreen suite, so the owner's Mac run is the
  evidence for the gate.
- **Startup**: decoding the six faces and building their mips takes 75–90
  ms on its own thread (71 ms in the unit test); uploading them takes 12–14
  ms on the main thread, once per run. The title shows the sky for those
  first frames; nothing waits.
- **Memory**: the panorama texture is 33,554,424 bytes on the GPU (six
  1024² faces with full mips); the UI atlas 1 MiB; the blur target a
  sixteenth of the window (about 0.5 MiB at 1080p). The software renderer
  keeps textures in system memory: peak RSS went from about 391 MB to
  about 472–480 MB, the texture plus the transient decoded faces and upload
  copy. The executable grows by the 3.5 MB of PNGs.
- **Icons**: one 64 x 64 PNG per world, about 10 KB; reading one is a
  file check and a 64 x 64 decode, at most four a frame.

## Differences from Java

- The panorama's content and wordmark are original, as required; the faces
  are 1024 x 1024 like Java's but are VoxelCraft terrain. There is no
  splash text, Edition line, Realms row or first-launch fade.
- The panorama's blur is VoxelCraft's: a disc of 13 samples at a quarter
  size, spread by Menu Background Blur (`BLUR_SPREAD` pixels a step),
  rather than Java's separable screen-space passes (which Track 2's world
  blur uses). It is cheaper over a panorama that turns every frame.
- Which way the panorama turns (clockwise from above, scenery drifting
  left) was chosen, not compared with a running Java client.
- The icon's section threshold is counted in 32-block chunk meshes (eight
  sections each), and "every section rendered" is "nothing left to generate
  or mesh". One capture runs at a time (Java could start a second if the
  write took over a second). Split-screen takes the first player's view.
  The shrink averages pixels (Java uses `NativeImage.resizeSubRectTo`).
  Icon files over 1 MiB aren't read.
- The empty list's message is VoxelCraft's; Java's list shows nothing.
- In 320 x 180 GUI-pixel windows, Reset Icon and Make Backup share a row.

## Review fixes (2026-11-24)

After merging `origin/v018-polish-performance` at `e8a502e`, two findings
from the integrated branch's review were confirmed in the code and fixed:

- **S7, a readback outliving its world.** `Game::into_shell` keeps the
  renderer for the title, and nothing cleared a pending icon request or
  readback, while `WorldIcon` wrote whatever frame came back. Leaving a world
  (`Renderer::clear_world`) now drops both, and a world writes a frame only
  while its own rule is waiting for one (`Capture::awaiting`).
- **S8, no result without `COPY_SRC`.** The copy returned early and left the
  capture in flight for good, so `--world-icon` waited forever. The renderer
  now reports the failure through `poll_icon`, and any read-back failure ends
  the visit's capture (`Capture::give_up`), which also releases a
  `--world-icon` screenshot.

- **S9, a dimension change dropping the frame** (round 2, after merging
  `a4d4787`). `Game::change_dimension` calls `Renderer::clear_world`, which
  since S7 drops a pending request or readback while the same `WorldIcon`
  stays waiting for it, so the capture hung. The renderer now counts the
  requests it drops (`icon_cancels`); a capture that sees the count change
  while it waits stops waiting (`Capture::canceled`) and takes the icon
  again once the destination has drawn, a second or more later.

`icons_only_accept_their_own_frame_and_give_up_when_unreadable` and
`a_dropped_icon_frame_is_taken_again_later` in
`tests/title_identity.rs` covers the rule's side; the renderer's side needs a
GPU surface and isn't unit-tested.
