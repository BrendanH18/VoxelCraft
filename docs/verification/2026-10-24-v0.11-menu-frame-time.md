# v0.11 menu and title frame time — 2026-10-24

[Roadmap](../roadmap.md#v011-scope-menus-and-settings) · [Requirement inventory](../requirements.md) · [Development: live scenes](../development.md#live-performance-scene-suite) · [M5 baseline](2026-10-16-m5-baseline.md)

Scope: v0.11's exit asks that "title and menu frame time stays within the M5
budget". The scene suite had no menu scenes, so this adds two and records a
first run. **The run is not acceptance evidence**: the machine was busy and
the display paced most frames at 120 Hz, so the gate check still needs an
idle-machine run.

## The new scenes

`benchmarks/scenes.json` now has seven scenes. The two new ones open each
screen in their `screens` list for two seconds in turn
(`performance::MENU_SCREEN_SECONDS`):

- **menus:** a world at spawn (seed 12345, view distance 256 blocks), the
  camera turning, with the pause menu, Options, Video Settings, Music &
  Sounds, Controls, Mouse Settings, Key Binds and Accessibility Settings,
  then the inventory. The pause screens stop the simulation, as Java's do.
- **title:** the title screen's turning sky with no world open: the title
  menu, Select World, Create New World, Multiplayer, Direct Connection,
  Options and its sub-screens.

Both use the reference configuration (1920 × 1080 physical pixels, enhanced
graphics, uncapped presentation, 10 s warm-up, 60 s samples, three repeats)
and ignore input. Because menus pause the game, these runs skip the tick and
pause checks; the title scene also skips the view-distance check. The runner
(`tools/benchmark_scenes.py`) applies the same rules, and its tests and the
`performance` tests cover them.

Run them on an idle M5 with:

```sh
caffeinate -dis python3 tools/benchmark_scenes.py --scenes menus,title,building
```

`building` is included as a control against the 2026-10-16 baseline.

## First run (not acceptance evidence)

Run by an agent on the reference M5 MacBook Pro while the owner was using it,
from the working tree after `5944be1` (uncommitted v0.11 finishing changes).
`node` used 123% CPU, a WebKit process 103%, the Metal shader compiler 83%,
and System Settings was open; the load average was about 4.

| Scene | Runs valid | 1% low FPS | p99 ms | p50 ms | Frames > 8.5 ms per run |
|---|---|---|---|---|---|
| menus | 3/3 | 96–179 | 2.87–8.38 | about 1.5 | 48–184 |
| title | 2/3 (run 3: window covered) | 97–113 (valid runs) | 5.2–8.0 (valid runs) | about 1.2–1.3 | 100–123 (valid runs) |
| building (control, 1 run) | 1/1 | 94.6 | 8.85 | — | 290 |

The title runs were measured with a sampler that also kept its 10 s of
warm-up frames (fixed in review the same day). The title row above drops the
first 10 s of each run's samples; the reports' own figures include them.

The control shows the run can't be trusted. On 2026-10-16 the building
scene scored 261–273 FPS 1% low with p99 about 3.1 ms. Here it scored
94.6, with about 6,300 of its roughly 7,200 frames held at the display's
8.33 ms pacing, the pattern the baseline attributes to display pacing. The baseline predates v0.9–v0.11, so
this run alone can't rule out a regression either. The menu screens add
little: median frame times are 1.1–1.6 ms on every screen, and the slow
frames are spread across all screens rather than at screen changes. In the
title scene they recur about once a second at around 20 ms even though it
draws only the sky and flat menus. That points to the busy machine, not menu
drawing, but only an idle-machine run can show it.
