## Behaviour and storage

- `world::maps` owns map centres, scales, dimensions, 128×128 packed colour
  images, target decorations, tracking/unlimited/locked flags and the map ID
  counter. Centre snapping uses Euclidean floor division, including negative
  coordinates, and scale sizes 128 through 2048. Scaling creates a blank image
  with a snapped centre; the scaling operation is available to callers.
- `Stack::map_id` is a final optional field in the existing stack-string
  format. Old strings keep loading. The lodestone field gets `~` when absent
  but followed by a map ID. Clones share a map ID; different maps do not merge.
- Maps and named loot-sequence states are saved in root `level.txt`
  properties (`maps`, `loot_sequences`) inside the existing world folder.
  These properties travel with the world when switching dimensions; image
  data is not duplicated into dimension folders. Old worlds without either
  property start with empty storage. Map images use hex bytes inside JSON.
- Shared session item use creates filled maps, transforms a final survival
  blank, consumes one blank from larger stacks and returns/drops the result,
  and keeps creative blanks. The same path handles the off hand and agents.
  The paper-around-compass recipe and map cloning preserve map components.
- Held maps update on desktop and agent/controller simulation ticks. The
  implementation follows `MapItem.update`: stripe/step selection, continuing
  through changed columns, modal colour with encounter-order ties, area
  heights and water depths, water/height brightness thresholds, circular
  radius and edge dithering, and the Nether ceiling-noise pattern. It reads
  loaded columns and never generates terrain to update an image.
- Biome preview uses the Java ocean/river/swamp outline scheme and quantized sine
  lookup. Explorer maps use temple random-spread ring searches, a village
  style ring search and scale 2. Buried treasure uses scale 1 once its locator
  is integrated. Missing destinations discard the loot stack or trade offer.
- Cartographer apprentice offers use the 26.3 biome-variant predicates, prices
  of eight emeralds plus a compass, 12 uses and 5 XP. The journeyman monument
  offer costs 13 emeralds plus a compass, 12 uses and 10 XP. Unsupported trial
  chamber/mansion destinations have no offer (including the master mansion
  map). A saved villager variant is initialized from its first observed biome.
  Map IDs are resolved before opening a merchant screen and persist in offers.
- Village chests belonging to a cartographer job use `village_cartographer`
  loot. Association is made from the owning template piece, including a job
  across a chunk boundary, rather than depending on registration order.
- First-person held maps draw a large centred image when the off hand is
  empty and a small image otherwise, also in split-screen views. Equal colour
  runs share a quad. Player arrows use quantized direction and coordinates;
  off-map players become edge markers. Targets use original structure silhouettes; treasure targets use an X.

## Java reference and extraction

Reference: the owner's extracted **Java 26.3** server classes/data, read as
behaviour facts. Classes inspected: `MapItem`, `EmptyMapItem`,
`MapItemSavedData`, `MapColor`, `ExplorationMapFunction`, `LootTable`,
`RandomSequences`, `RandomSequence`, `RandomSupport`, `XoroshiroRandomSource`,
`Xoroshiro128PlusPlus`, `EnchantRandomlyFunction` and `EnchantmentHelper`.

`tools/java_block_properties.py` now records `mapColor` alongside the existing
mining properties without changing its mining tuple API. It evaluates known
colour-enum branches, constant/default block colours, axis-dependent logs,
bed parts and waterlogged map-colour functions. The fixture
[`map_colors.json`](../../tests/fixtures/java/26.3/map_colors.json) records
1,286 registrations, including explicit nulls for unresolved state functions.
`tools/extract_java_map_colors.py` regenerates it from the classes jar and
`MapColor.java`. Runtime resolves axis, bed-part and waterlogged rules, uses
Java's 62 base colours and brightness multipliers 180/220/255/135, and has a
small documented material fallback in `maps::block_color`.

`tools/extract_java_structure_loot.py` normalizes the 26 supported structure
chest tables and the enchantment/tag inputs into
[`loot_tables.json`](../../src/world/loot_tables.json). This is behaviour data,
not artwork. Declaration order, weights, number providers and modifiers are
retained. Unsupported inventory entries execute their random modifiers and
are discarded before filling. All seven existing structure-chest families use
this path; saved containers still win over newly rolled loot.

`world::loot` implements Java's seeded LCG (`enchant::JavaRandom`), Xoroshiro
128++ state transitions, MD5 key hashing in big-endian longs, Stafford13 seed
mixing, unsigned bounded Xoroshiro draws, and default named sequence seeding
(world seed plus sequence ID, salt zero). A zero or absent world loot seed
uses the table's persistent named sequence. Explicit nonzero seeds use the
LCG. Pool rolls and weighted choices precede available-slot shuffling,
`shuffleAndSplitItems`, final item shuffling and reverse slot-list placement.
The interpreter preserves function order for counts, damage, random/level
enchantments, goat horns and exploration maps.

`tools/JavaLootVectors.java` is an independently written oracle using JDK
`Random`, `Collections.shuffle` and `MessageDigest`. It records cartographer
pool/slot vectors and MD5/Xoroshiro vectors; no decompiled implementation is
copied into that oracle.

## Integration and known gaps

- **New structure tables:** parallel tracks adding ruined portals, buried
  treasure or other loot must add their table names to the extractor and use
  `World::structure_loot` (or `loot::table` with an explicit seed). The original
  `bastion::pool`/`put` helper signatures are retained for merge compatibility;
  those compatibility helpers do not implement the new fill ordering.
- **Required integration:** `maps::buried_treasure` intentionally returns
  `None` at `// v0.14 integration: buried treasure locate`. Wire it to the
  other track's `generator.buried_treasure.nearest_buried_treasure(g, from,
  max_rings)`. Until then shipwreck/ruin treasure-map entries are discarded.
- Existing terrain and structure placements are VoxelCraft's; a map points to
  its actual structure, and is not proof of Java terrain/seed parity.
- The ring searches do not claim/reference structures (`skip_known_structures`)
  or exclude previously explored starts. Repeated offers can point to the same
  destination. Existing villager tier offer selection remains VoxelCraft's
  seeded reservoir, not Java's trade-set random sequence; variant is first
  observed biome rather than a fully modelled birth variant.
- First-person presentation uses the existing VoxelCraft hand renderer and
  does not reproduce Java's two visible arms or pitch-dependent map animation.
  Item-frame map images and banners are not implemented; frames retain item
  sprites. LAN stack IDs remain serializable, but images are not synchronized.
- Map scaling maths exists; scaling/locking through cartography-table or
  crafting UI is not wired. Maps do not inherit Java's NBT/components format.
- Null map-colour fixture entries remain gaps. Copper weathering uses the
  documented Java colour table (orange / terracotta light gray / warped stem /
  warped nylium). Other unresolved or VoxelCraft-only names fall back to the
  explicit common-material table, leaves/plants green, uncoloured glass and
  torches transparent, otherwise stone. This is not full per-state parity.
- Unsupported enchantments keep their selection/level draws but cannot be
  represented in the existing 33-enchantment stack bits. Unsupported gear is
  discarded. Virtual spear enchantability follows the material's existing
  value; full 26.3 spear/component coverage is outside this track. The
  mineshaft entry requiring sulfur caves is excluded before weighting, since
  this generator has no sulfur-caves biome.
- Persistent named-sequence default seeding is implemented. Java command
  overrides for sequence salt/world-seed/ID inclusion are not exposed.
- Hands-on game tests, held-map/explorer-map screenshots, frame-time evidence
  and the owner's ordinary play remain unverified. No game process was left
  running. This Sol implementation agent did not delegate or perform Terra
  computer-use work.
