## What changed

The redstone engine used to put neighbour notifications in a deduplicated
FIFO over a fixed two-block neighbourhood, drained once per tick, and
scheduled ticks in a heap. It now follows Java 26.3's update order
(`src/world/redstone_order.rs`, with the block behaviour in
`src/world/redstone.rs`):

- **Neighbour updates** run on a port of `CollectingNeighborUpdater`. Each
  outermost call runs to completion at once, and nested calls join the
  current layer, depth first. `updateNeighborsAt` visits neighbours in
  `NeighborUpdater.UPDATE_ORDER` (west, east, down, up, north, south), with
  `updateNeighborsAtExceptFromFacing`'s skipped side. Shape updates go in
  `UPDATE_SHAPE_ORDER` (west, east, north, south, down, up). Java's limit of
  1,000,000 chained updates per outermost run replaces the old 65,536-update
  carry-over budget: past the limit, updates are dropped with Java's log
  message.
- **`Level.setBlock`.** `World::edit` (and `World::set_block_flags`, which
  takes Java's flags) applies these effects in Java's order: the old block's
  `affectNeighborsAfterRemoval`; the new block's `onPlace`, called on every
  state change; `updateNeighborsAt` when `UPDATE_NEIGHBORS` is set; the
  comparator notification (`updateNeighbourForOutputSignal`); and, unless
  `UPDATE_KNOWN_SHAPE` is set, the old wire's indirect shape updates, the six
  shape updates and the new wire's indirect shape updates. These run after
  every other effect of the edit (lighting, block entities, remeshing). An
  edit made between ticks now updates synchronously, as Java's does.
- **Wire** follows `DefaultRedstoneWireEvaluator`. Power is set with
  `UPDATE_CLIENTS`, then `updateNeighborsAt` runs on the wire and its six
  neighbours in `java.util.HashSet` iteration order. That order is the
  bucket of `Vec3i.hashCode`'s spread hash in a 16-bucket table, then
  insertion order (`redstone_order::java_hash_set_order`). Wire `onPlace`
  and `affectNeighborsAfterRemoval` are ported, with
  `updateNeighborsOfNeighboringWires` and `checkCornerChangeAt`; a wire that
  loses its support breaks on its `DOWN` shape update or its neighbour update.
- **Diodes.** `DiodeBlock.checkTickOnNeighbor` uses Java's priorities:
  EXTREMELY_HIGH when the block in front is a diode not facing back, else
  VERY_HIGH when turning off, else HIGH, and skips if `willTickThisTick`.
  The comparator schedules HIGH or NORMAL and also compares its powered
  state; ticks set the state with `UPDATE_CLIENTS`. `updateNeighborsInFront`
  runs on every state change (`onPlace`) and removal, and
  `refreshOutputState` runs it again. A diode that loses its support drops
  and updates its neighbours' neighbours. Using a comparator sets it with
  `UPDATE_CLIENTS` and refreshes it.
- **Comparator side input** follows Java's `getControlInputSignal`: a
  redstone block reads 15 and wire its raw power. Before, a redstone block
  read 0.
- **Torches** schedule with NORMAL priority unless `willTickThisTick`.
  `onPlace` and removal notify all six neighbours' neighbours. Burnout keeps
  Java's `RECENT_TOGGLES` window per torch (prune entries older than 60
  ticks; the eighth off-toggle schedules a 160-tick tick; relight only with
  fewer than eight). The separate burnout deadline is gone, so a burned-out
  torch relights on the tick Java's does.
- **Levers and buttons** use `pull`/`press`: set with `UPDATE_ALL`, then
  update around the switch and its support. Button release and the removal
  of a powered switch do the same.
- **Pressure plates** set their power with `UPDATE_CLIENTS`, then update
  around the plate and below it (`checkPressed`). The entity-contact path
  does this too.
- **Lamps, doors, trapdoors, gates and hoppers** change with
  `UPDATE_CLIENTS`, as Java's do, so they no longer send neighbour updates.
- **Observers** react only through shape updates from their watched face
  (`updateShape`, `startSignal` if no tick is pending). Their tick sets the
  state, schedules the off tick, then updates in front. `onPlace` and
  removal are ported, and a powered observer loaded without its tick gets one.
- **Attached blocks.** Levers, buttons, torches, plates and wire break on
  the shape update from their support (Java's `updateShape`).
- **Scheduled ticks** follow `LevelTicks`. Each tick first collects every
  due tick, up to 65,536, and a collected tick no longer counts as
  scheduled (`willTickThisTick` covers that gap). Ticks are ordered by
  trigger tick, then priority, then sub-tick order. Overdue ticks are
  merged across chunk columns as `drainContainers` does. Ticks scheduled
  while they run wait for a later tick, so a 0-delay tick runs on the next
  tick.
- **Block events** follow `Level.blockEvent` and
  `ServerLevel.runBlockEvents`: an insertion-ordered set (an identical
  event is queued once), drained at the end of the tick, events added
  during the drain included. Events at cells that aren't ticking wait. A
  run event checks that the block is still the one that queued it. Pistons
  queue `TRIGGER_EXTEND` (0) or `TRIGGER_CONTRACT` (1) with the facing's
  `get3DDataValue` from `checkIfExtend` (on neighbour updates and
  `onPlace`), and `World::piston_trigger_event` rechecks power when the
  event runs. Today's piston moves are unchanged behind it.
- **Tick phases.** `simulation::tick_world_rules` now runs the block ticks
  first and the block events after the random ticks, as `ServerLevel.tick`
  does (see [Tick phases](#tick-phases)). `World::tick_redstone` still runs
  both, for headless callers.
- **The saved `redstone` property** is now `v2`. It adds queued block events
  (`e`) and no longer writes a torch burnout deadline (`b`) or toggle
  history (`h`; Java's `RECENT_TOGGLES` is memory-only). v1 saves still
  load; their `b` entries are ignored and their `h` entries still load.
- **Tracing.** `World::trace_redstone` records every executed neighbour
  update, shape update, scheduled tick and block event (`Traced`), for the
  order fixtures and for debugging.

### API for other tracks

- `World::queue_block_event(pos, block, a, b)` queues a `BlockEvent`
  (deduplicated; the block is stored as its family).
  `World::block_events()` lists the queue.
- `World::run_block_events()` drains the queue; `tick_redstone` and
  `tick_world_rules` call it.
- `World::trigger_block_event(event)` dispatches `triggerEvent`; today only
  pistons answer, through `World::piston_trigger_event`.
  `automation::PISTON_EXTEND`, `PISTON_RETRACT` and `PISTON_RETRACT_SHORT`
  are Java's event numbers.
- `World::set_block_flags(p, block, flags)` with `redstone_order::flags`
  (`UPDATE_NEIGHBORS`, `UPDATE_CLIENTS`, `UPDATE_KNOWN_SHAPE`,
  `UPDATE_MOVE_BY_PISTON`, …) is `Level.setBlock`. Moving pistons should pass
  `UPDATE_MOVE_BY_PISTON`, which skips the removal effects that check
  `movedByPiston`.
- `World::update_neighbors_at`, `update_neighbors_at_except`,
  `neighbor_changed_at` and `neighbor_shape_changed` (crate-visible) are
  Java's `Level` calls of the same names.
- `World::batched(f)` runs `f` with its updates queued until it returns. It
  is for VoxelCraft behaviour that edits several cells, not for ported Java
  behaviour.
- `World::trace_redstone(on)` and `take_redstone_trace()` record the order.

## Fixtures

`tools/extract_java_redstone_order_fixtures.py` writes
`tests/fixtures/java/26.3/redstone_order.json`. It checks the pinned jar's
hash, reads these facts from the bytecode, and fails on any form it doesn't
expect:

- the direction orders listed above, and the `TickPriority` values;
- the chained-update and scheduled-tick caps;
- the call order inside `Level.setBlock` and `LevelChunk.setBlockState`,
  and the `-34` neighbour-flag mask;
- the evaluator's `Sets.newHashSet` / `Direction.values()` update set;
- `Vec3i.hashCode`;
- the diode, comparator, torch, lamp and observer delays and priority
  fields;
- the `ServerLevel.tick` phase order and the block-event set.

It then runs an independent model of those classes, written from the
decompiled source without reading VoxelCraft code, over seven contraptions.
It records each one's per-tick states and the order its neighbour updates,
shape updates, scheduled ticks and block events ran (entries at air or
stone left out):

| Case | What it pins |
| --- | --- |
| `wire_line_order` | A redstone block placed beside, then removed from, a three-wire line: all 33 and 207 updates in Java's order (the `HashSet` order, the depth-first stack, shape and indirect shape updates). |
| `repeater_lock_race` | One lever powers a repeater and the side repeater that locks it (both delay 1): the locking repeater's EXTREMELY_HIGH tick runs first and the other never turns on. |
| `torch_burnout` | A wall lever toggled 16 times: eight off-toggles in 60 ticks burn the torch out. A neighbour update at tick 120 can't relight it early, because its pending 160-tick tick blocks a new tick for the same block. It relights on tick 204. |
| `piston_qc_bud` | A redstone block diagonally above a piston powers it only through quasi-connectivity and sends it no update; a neighbour update three ticks later queues the extend event, which runs at the end of that tick. |
| `observer_clock` | Two observers facing each other: shape updates start each pulse, and the set-then-schedule order gives a six-tick period. |
| `comparator_modes` | A three-tick lever pulse into a comparator whose side reads a wire at 14: compare mode passes 15, and after a use subtract mode passes 1. |
| `priority_race` | One lever schedules an EXTREMELY_HIGH repeater, a HIGH repeater, a NORMAL comparator and a NORMAL wall torch in one tick, in priority then sub-tick order. The pull back gives the turning-off priorities. |

The model's limits, which the cases avoid: it derives wire connections from
the neighbours as `getConnectionState` would set them, its pistons stop at
the extension event, and it has no containers.

## Tests

`tests/redstone_order.rs` rebuilds each case through the game's own entry
points (`set_block`, `use_redstone`, `tick_redstone`). It compares every
tick's watched states and the update logs, and checks the extracted orders
and constants against `redstone_order`'s. It also checks the `HashSet`
order at two positions, and that block events are deduplicated and wait
for the end of the tick. All nine tests pass. The lock race compares only
its tick order (see the first difference below).

Existing tests whose expectations changed, all because Java's timing or
behaviour differs from the old engine's:

- **Torch, repeater, lamp and save round-trip tests**
  (`world::redstone::tests`): edits now update synchronously, so a change
  made between ticks reaches its scheduled tick one tick earlier. This is
  Java's timing: torch 2, repeater 2 × delay, lamp 4, counted from the edit.
  The burnout test now checks the toggle history and the 160-tick relight.
  The round trip checks the v2 header and that a v1 save's `b` entry is
  dropped.
- **`powered_wire_strongly_powers_its_support_and_pointed_solid`**: a
  placed wire takes its real power at once (`onPlace`), so the test powers
  it to 9 through a line instead of placing a `wire(9)`.
- **`comparators_compare_subtract_and_read_container_fullness`**: a placed
  `wire(1)` with no source is 0 at once. The side input is now a redstone
  block, which reads 15 (`getControlInputSignal`); before, it read 0.
- **`wood_track::new_states_survive_a_file_save_and_reload`** stacked its
  layers two blocks apart, so a powered button placed on the next layer's
  support stone now powers the trapdoor beneath it at once (before, nothing
  propagated without a tick). The layers are now three blocks apart.
- **Dropper and hopper tests** (`world::automation::tests`): droppers fire
  4 ticks after the power edge (`DispenserBlock`'s 4-tick tick), and a new
  hopper transfers on its first tick (Java's cooldown starts at -1), one
  tick earlier than before.

## Differences from Java

1. **Repeater `LOCKED` is derived, not stored.** In Java, locking or
   unlocking a repeater is a `setBlock` that runs its `onPlace`
   front updates, and observers see it. VoxelCraft has neither. The lock
   itself acts identically, because Java's `tick` and `checkTickOnNeighbor`
   read the live lock, not the property. A stored lock would need new
   states; Track A's reserved 12800–12831 (32 states: 4 facings × 4 delays
   × 2 powered) would fit it, but are unused.
2. **Wire connections are derived.** Java's wire connection changes are
   `setBlock`s with further shape updates. VoxelCraft sends the shape and
   indirect shape updates but changes nothing in them. Toggling a dot or
   cross by hand doesn't run `updatesOnShapeChange`.
3. **Plain `World::edit`** (players, other systems, tests) adds
   compatibility notifications (`flags::COMPAT`) that Java gets from code
   not ported here:
   - A switch or plate written directly in a new powered state updates as
     its toggle would.
   - Strong sources whose own update calls aren't ported (detector rails,
     tripwire hooks, lightning rods, lecterns, trapped chests, sculk
     sensors) update around the block they strongly power, after the
     edit's own updates. Java does this inside each block's code,
     sometimes in another order.
   - A newly placed block without a ported placement check (hoppers,
     rails, TNT, note blocks, bells, daylight detectors, lamps, doors)
     checks itself at the start of the next tick, before the clock
     advances. This stands in for the various `onPlace`, `setPlacedBy` and
     `getStateForPlacement` checks.
   - Placed repeaters and comparators follow `DiodeBlock.setPlacedBy` (a
     1-tick tick if they should turn on). Java does that only for player
     placement, not `/setblock`.
4. **Deferred `redstone_changed`.** Container, sensor, cart, item-frame and
   tripwire notifications run at the start of the next tick, before the
   clock advances, because callers notify before they finish mutating
   (`chest_mut`). Java notifies at the change. Scheduled timing is the same;
   the order within the tick differs.
5. **Batches.** Behaviour that is not yet ported Java runs as one batch, its
   updates queued until it returns: piston moves inside their block event,
   finishing piston moves, tripwire hooks and strings, rail and detector
   ticks, the entity-contact refresh, and the scheduled ticks of
   non-redstone blocks.
6. **Non-ticking cells.** Neighbour updates to cells that are loaded but
   not ticking are parked until the cell ticks; Java runs them on any
   loaded chunk. Updates to unloaded cells do nothing, as in Java.
7. **The 65,536-tick cap** is applied to the globally earliest ticks;
   Java's merge applies it per column. This differs only with more than
   65,536 due ticks, overdue ones among them in several columns.
8. **Shape updates** don't track the 512 recursion limit; VoxelCraft's shape
   reactions only break attached blocks.
9. **Pistons** queue their event without `PistonStructureResolver.resolve`'s
   pre-check, never use `TRIGGER_DROP` (2), and retry 2 ticks later while
   their blocks still move. Moves finish at the start of the next tick
   rather than in the block-entity phase. Track B owns the piston
   arbitration.
10. **`hasAnalogOutputSignal`** is "the comparator reads something here"
    (`container_signal`).
11. **`RECENT_TOGGLES`** is kept per torch rather than in one list per
    level; the counts are the same.

## Tick phases

`ServerLevel.tick` runs, in order: block ticks, fluid ticks, raids, the
chunk source (random ticks, spawning, precipitation), block events, then
entities and block entities. VoxelCraft's `simulation::tick_world_rules`
now runs:

1. block ticks: every scheduled tick, redstone and non-redstone, in one
   queue, with deferred notifications and piston-move completion first;
2. sculk;
3. fluids;
4. falling blocks;
5. furnaces and brewing stands;
6. utilities and jukeboxes;
7. fire, light, precipitation, random ticks and leaf decay;
8. block events.

Entities follow in the caller, with `tick_automation_entities` after
them. The differences from Java's order:

- Furnaces and brewing stands (block entities in Java) run before random
  ticks and entities.
- Hoppers run as scheduled ticks rather than block entities.
- Raids run in the session, not here.
- Piston moves finish at the start of the next tick.
- Fluid ticks are VoxelCraft's own queue, which runs after the block ticks
  as Java's fluid ticks do.

## Performance

This is the ignored benchmark `world::redstone::tests::dust_grid_benchmark`,
run on the Boat `large` sandbox (8 vCPUs). The new engine's numbers are
from this branch; the old engine's are from `main` at `8d49f02` in the same
sandbox. A redstone block is placed on and removed from the centre of a
128 × 128 dust grid.

| | Power up | Power down | Idle tick |
| --- | --- | --- | --- |
| Old engine | 11.4 ms, 17,411 updates | 5.7 ms, 1,785 updates | 3 ns |
| Java order | 14.5–16.8 ms, 31,788 updates | 26.3–34.0 ms, 59,532 updates | 11 ns, 0 updates |

The Java order is costlier on wire power-down, as Java's
`DefaultRedstoneWireEvaluator` is. A 16-wire line powered and unpowered
costs 1.36 ms per pair, almost all of it in the edits' lighting and
remeshing bookkeeping. Idle circuits still do no updates and allocate
nothing. At the measured ~0.5 µs per update, a contraption that reaches
Java's 1,000,000-update chain limit would stall that tick for about half a
second, as it would in Java. The frame-time suite needs the reference Mac
and has not been run.

## Follow-up after the merge (2026-11-23)

On `v017-a-fixes`, from the merged `v017-redstone-automation` (`e9c9395`),
two persistence failures in Track F's
[contraption corpus](2026-11-23-v0.17-reference-contraptions.md) were fixed:

- **Chunk loads re-evaluated every component.** `load_redstone_chunk`
  queued a refresh of each redstone component in a loaded chunk, a
  leftover of the old engine. Java re-evaluates nothing on load, so after a
  save and restart the BUD switch's quasi-powered piston fired, and after
  an unload a burned-out torch scheduled a check and relit once its
  toggles aged out. The refresh is gone; only a powered observer whose old
  save lost its tick still gets one.
- **Toggle history is no longer saved.** Java's `RECENT_TOGGLES` lives in
  memory only, so a restart mid-toggling starts the count again.

Two of Track F's Java expectations were wrong and were checked on the
vanilla 26.3 server (see that record's follow-up): the observer clock's
period is 6, matching this engine and the `observer_clock` fixture, and
a torch never sees a 2-tick observer pulse, so the T flip-flop build
doesn't toggle in Java.
