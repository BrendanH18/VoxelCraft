### Jukebox and music

- Use (shared `PlayerSession::use_held`, so desktop, controller, CLI agents
  and LAN players all get it): a jukebox holding a record pops it out
  (above the block, into `World::drops`) whatever is held; an empty one takes
  a held disc and plays it (Creative keeps the disc, `consumeAndReturn`).
  Sneaking with an item skips it, as for other blocks. `Used::Jukebox`.
- Playback follows `JukeboxSongPlayer`: ticks counted from 0, `jukebox_play`
  every 20 ticks with a note particle (`nextInt(4) / 24` tint), the song
  ends at `ceil(seconds * 20) + 20` ticks, the record stays. Weak redstone 15
  to every side while playing; comparator output by the record's song
  whether playing or not (`getComparatorOutput`).
- Hoppers insert discs into an empty jukebox (it plays) and take the record
  out (the song stops, nothing pops), as Java's one-slot container does.
- Breaking a jukebox pops its record (`preRemoveSideEffects`) and stops it.
- **Tunes**: each disc has an original seeded arrangement (key, mode, tempo
  in whole ticks, lead/bass instruments, chord progression, A A B A motifs,
  intro and closing bar, optional arpeggio and percussion) played tick by
  tick through the existing note-block voices in `SoundSource::Records`, for
  exactly its Java length. The score is a pure function of the disc and the
  tick, so a reloaded jukebox resumes in place. LAN clients hear it through
  the host's sound tap. "Now Playing: Music Disc …" shows within 64 blocks
  (level event 1010; the disc's name stands in for Java's artist credit).
- **Game events / allays**: `World::jukebox_events` carries `jukebox_play`
  and `jukebox_stop_play`. The entity pass (`Entities::hear_jukeboxes`)
  drains them, sets allays within the event's 10-block radius dancing (or
  stops them) via the existing `set_jukebox_playing`, and offers each event
  to `jukebox::vibration_hook` for track A. Allays now also stop dancing
  every 20 ticks when the jukebox is out of range or gone
  (`shouldStopDancing`), and a dancing allay duplicates with an amethyst
  shard through the existing callback.
- Save/reload: per-dimension `jukeboxes` key (`[[x,y,z],"stack",ticks|null]`;
  empty jukeboxes aren't saved). A song saved after it finished doesn't
  resume (`setSongWithoutPlaying`).

### Recovery compass and Swift Sneak

- `PlayerSession::last_death` records the dimension and `blockPosition` the
  first tick a player is dead, on every path (it runs with the lodestone
  tick). Saved as `last_death` for the host player and in each agent/LAN
  profile; survives respawn; replaced by the next death. The compass needle
  points to it in that dimension and wobbles otherwise
  (`CompassAngleState`'s `RECOVERY` target). Agents see it in their
  observation (`recovery_compass`).
- `Enchantment::SwiftSneak` (save bit 40): weight 1, max III, costs 25+25 /
  75+25, anvil cost 8, leggings only, treasure, excluded from the enchanting
  table, `#on_random_loot` and librarian trades. Effect: the sneaking speed
  attribute is 0.3 + 0.15 per level (clamped to 1), read from the worn armor
  every tick on every input path.

## Known differences and gaps

- Templates are original and smaller than Java's (a 43-block centre, 15-block
  walls); layouts can't match Java seeds. Skeleton skulls (heads aren't
  implemented), redstone lamps/comparator props, stairs, ladders, and
  hidden rooms are not modelled; all pieces share one floor height.
- `beard_box` is approximated by the carve-and-fill above; Java's smooth
  density kernel (12-block falloff) isn't reproduced. Underground lava or
  water beside a carved margin can flow in when the chunk ticks.
- The sculk patch reproduces the feature's look (sculk, veins, catalyst,
  shriekers), not `SculkSpreader`'s charge-by-charge growth. Decisions use
  hashes, not Java's random sequence.
- `protected_blocks` (`#features_cannot_replace`) isn't applied; painting
  carves first, so nothing protected is in the way except bedrock below.
- Loot entries still blank: `experience_bottle` and the ward/silence armor
  trim templates (not implemented items); suspicious stew effects aren't
  stored (an existing gap).
- **Ancient city explorer maps**: in Java 26.3 only
  `chests/abandoned_camp_secret_chest` names `buried_ancient_city_map`;
  VoxelCraft has no abandoned camps, so no map item or table was added.
- Music: records are heard within the mixer's fixed 24-block falloff (Java's
  record sound is linear to 64 blocks); background music isn't ducked while
  a record plays. Java's music (C418 etc.) is not reproduced: tunes are
  original.
- The jukebox popping its disc uses the world drop path (Java spawns it at
  +1.01 with a ±0.35 random offset and the default pickup delay).
- Vibrations: `jukebox::vibration_hook` is a no-op until track A wires it.
- Trail ruins' archaeology (`music_disc_relic`) isn't implemented (trail
  ruins use plain gravel, DEF-02), so relic is creative-only; trial vault
  discs are track C's (resolvable by name: `Item::from_name`).
- Not run: the game (no screenshots, hands-on or LAN play), benchmarks and
  frame-time scenes; cities' chunk-generation cost isn't measured.

## Integration hooks

- `world::jukebox::vibration_hook(world, pos, event)`: call track A's game
  event emission there (`game_event_name` gives `jukebox_play` /
  `jukebox_stop_play`).
- Summoning shriekers: cities place `sculk_shrieker(false, true, _)`; track
  A's shrieker logic needs nothing else.
- Track C vault loot naming discs (`music_disc_creator`, `precipice`, …)
  resolves through `Item::from_name` / `jukebox::disc_named`.
- Icons: track B appends 25 icons at `passive_icon_base() + 19` and 32
  animated recovery-compass frames after the clock frames (effect icons
  move after them). Block texture `COUNT` includes `jukebox::t::END` (3669).
- Enchantment save bit 40 is Swift Sneak; `COUNT` is 41 here (track D's
  Wind Burst appends at 41). The librarian pick draws from the first 40.
- Jigsaw: `jigsaw::all()` now lists `ancient_city`; `assemble_with` and the
  `cell` line are available to other tracks (trial chambers).
