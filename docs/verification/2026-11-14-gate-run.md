stalls per run were traced to explorer maps rolled on the main thread and
moved to the generation workers.

## The streaming stalls

Each run has exactly two frames over 50 ms, in both suites: about 290 ms
134.5 s into the route and about 200 ms at 171.6 s. The 2026-11-11 run had
the same pair (worst 293–296 ms). They come at the same places every time,
so they come from the route, not the machine.

A temporary build printed the frame phases of any frame over 50 ms and then
timed the steps inside it. All of each stall was in the frame's streaming
step: `World::update_players` installing a freshly generated chunk, and in
it `register_features` rolling a structure chest's loot. The chests are
shipwreck or ruin chests holding a buried treasure map. Rolling the map
locates the treasure (15–20 ms) and then draws the map's biome preview
(100–194 ms), which samples the biome under each of the 128 × 128 pixels:

| Route time | Chunk | Locate | Preview |
|---|---|---|---|
| 134.5 s | (60, 1, −8) | 20.3 ms | 101.1 ms |
| 134.5 s | (63, 1, 1) | 15.7 ms | 130.2 ms |
| 171.6 s | (77, 1, 1) | 17.1 ms | 193.9 ms |

Two of the chunks arrived in the same frame, hence the larger first stall.

Java rolls a structure chest's loot only when the chest is first opened, so
its map work is a hitch when the chest is opened rather than during
streaming. VoxelCraft rolls the loot when the chunk is installed, which
also numbers a map for every such chest, opened or not. Both behaviours
stay as they were here; matching Java's lazy loot is a larger change to
every chest access.

## Fix

`GeneratedChunk::new`, which runs on the generation workers, now rolls each
seeded structure chest the chunk places (`loot::RolledChest::roll`),
drawing any explorer map with `maps::explorer_map`. The main thread then
only numbers the maps, in roll order, and installs the chest
(`World::number_maps`). Unseeded chests, which draw on the world's loot
sequences, and chests a save already holds are still handled on the main
thread as before. `worker_rolled_chests_match_main_thread_rolls` rolls the
shipwreck map chest from the stalling route both ways and checks the chest,
its map numbers and the saved maps are identical.

Three offscreen streaming runs with the fix (`5b367d71`, 17:55–18:05, same
machine and conditions), kept in
[2026-11-14-5b367d7-m5-streaming-offscreen](../../benchmarks/results/2026-11-14-5b367d7-m5-streaming-offscreen/):

| Build | Run 1 | Run 2 | Run 3 |
|---|---|---|---|
| `1ee87eb1` | 201.8 / 3.17 (562; 297.7) | 214.3 / 2.99 (567; 293.2) | 215.0 / 2.99 (564; 293.2) |
| `5b367d71` | 232.0 / 3.21 (556; 12.3) | 232.5 / 3.22 (554; 13.2) | 232.7 / 3.21 (554; 15.3) |

No frame reaches 50 ms (worst 15.3 ms), no simulation time is discarded,
and the game marks all three runs as passing. The slowest 1% of frames now
average 4.3 ms, 2.7–2.8 ms of it in ticks and 0.7 ms in streaming.

The three windowed streaming runs started after them are invalid: the
Mac's screen locked at about 18:00 and hid the window, so the runner
counted about 15,000 unpresented frames in each. They are not kept.
