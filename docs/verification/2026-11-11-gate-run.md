### Defect: oversized effect swirls (fixed)

Right after `/effect give @s speed 300 0`, large cyan squares covered much
of the view. They are the player's own Speed swirls, spawned around the
body and drawn a few centimetres from the camera, where one sprite pixel
covers a large part of the screen. Java draws your own swirls in first
person too: 26.3's `SpellParticle` hides them only while you look through a
spyglass (`isCloseToScopingPlayer`). But `LivingEntity.tickEffects` in the
26.3 client jar (read with `javap -c`) spawns one on a `nextInt(4) == 0`
tick (15 while invisible, times 5 for ambient effects) and takes the
particle of one active effect with `Util.getRandom`. VoxelCraft spawned on
every other tick and blended the colours of all active effects.

Fixed in `1bbd9319`: `particles::ambient::System::effects` now uses Java's
odds and one randomly picked effect's colour. No ambient effects exist yet
(beacons are v0.18). `effect_swirls_follow_java_odds_and_take_one_effect_colour`
counts about 1,000 swirls in 4,000 ticks with two effects, each in one pure
colour, and about 267 while invisible. It fails on the old code. Not seen
in the game after the fix.

## Follow-up: instrumentation and aiming commands

Done the same day while the owner used the Mac, so nothing below was run
on it. Both changes passed `scripts/remote-check.sh --full` on Namespace
Linux.

**Frame pacing instrumentation.** Benchmark runs now time each frame's
render passes on the GPU where the adapter has `TIMESTAMP_QUERY`, read back
through a ring of buffers so no frame waits; a frame whose slot is still
busy goes untimed, so check the timed and missed counts before reading the
GPU figures. Reports add `frame_gpu_ms`
and `frame_acquire_ms` per frame, and GPU time for the slow-acquire frames
apart from the rest. The runner takes `--frame-latency`, `--window-mode`
and `--no-gpu-timestamps`. A non-default frame latency or window mode
marks the run a presentation experiment that can't pass the gate; turning
GPU timing off doesn't. The commands are in
[presentation experiments](../development.md#presentation-experiments).

Reading wgpu-hal 30 settled one hypothesis without a run. Metal reports a
frame latency range of 1..=2, wgpu-core clamps the request to it, and the
layer's `maximumDrawableCount` is latency + 1. The current setting of 2
already gives three drawables, the most a `CAMetalLayer` allows, so the
matrix compares latency 1, not 3. wgpu already turns `displaySyncEnabled`
off for Immediate mode.

**Steady-state regression candidates (code reading only).** In the 11-11
runs an average frame spends about 1.3 of 1.9 ms acquiring a drawable and
about 0.55 ms in the game's own work, so the drop from the 2026-10-16
baseline most likely comes from GPU work. Candidates, most likely first:

1. Texture paging (`05831cda`): the block texture count passed 2048, the
   Apple GPU array limit, so every chunk, model, entity and particle pixel
   now takes the paged path in `chunk.wgsl`. Its cost was never measured
   alone.
2. Different scene contents: v0.13 terrain and v0.14 structures change what
   the seed-42 scenes draw.
3. The v0.11 Brightness curve in every lit shader (probably minor).
4. Mobs drawn as GPU instances (`2c8c173e`), mainly in the entities scene.

The CPU-side additions each frame (signs, shelf and brushable items) were
ruled out: that phase measures about 0.01 ms.

**Aiming commands.** The hands-on agent couldn't turn the camera. Java's
`/tp @s x y z yaw pitch`, `/tp @s x y z facing x y z`, `/tp … facing
entity @s [eyes|feet]` and `/rotate` now work in the console and for the
CLI agent, with Java's angles and block-centre positions. As in Java,
`facing` looks from the feet. Only `@s` and `@p` are targets, so facing
another entity needs its coordinates. The camera snap is covered by tests,
not yet seen in the game.
