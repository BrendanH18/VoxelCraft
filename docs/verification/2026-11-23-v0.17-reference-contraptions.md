## What was built

`tests/contraptions/` is one integration test target (`cargo test --test
contraptions`):

- `rig.rs` is the harness. A build is a list of block states at relative
  positions (or ASCII layers through `grid`), container contents, a
  set-up hook, a per-tick script (a player's presses and edits, which
  land between two server ticks), a set of probes, a tick count and its
  interruption points. The rig runs it in a headless flat world through
  the systems `Game::tick` runs, in its order: carts, contact inputs,
  `tick_world_rules` (redstone, fluids, furnaces, random ticks), automation
  entities, per-chunk entity storage, entities, then block drops become
  item entities. After every tick it records each probe: a block state,
  redstone power, a container's items (all or one kind), the position of
  the first block of a kind in a row, a cart's position and items, loose
  items, blocks in piston motion, the remaining delay of one position's
  scheduled tick, and a hash of every pending scheduled tick (position,
  remaining delay, priority, as the `redstone` save records them). It also
  totals items in every container, furnace, cart and loose item plus a
  build's counted blocks (moving ones included).
- The three interruptions: **unload** every storage column the build
  touches for 37 game ticks while the world keeps ticking, then load them
  back (`World::unload_test_column`, `load_test_column`: the real
  `remove_chunk` and `insert_chunk` paths, with entities going to and
  from per-chunk storage); **restart**: save the world with every
  dimension property `Game::dimension_props` writes and the entity
  properties to a real `Storage` directory, drop the world, and load a
  fresh one from disk the way `Game::restore_dimension` does; and
  **restart mid-motion**: the same restart at the first tick (from a
  build's `motion_after`) with blocks in piston motion, or, for builds
  without pistons, with scheduled ticks pending.
- `check` runs the reference and the three interruptions and requires:
  the build's Java behaviour (`verify`) on every run; for deterministic
  builds, every interrupted trace equal to the uninterrupted one tick for
  tick, the pending-tick hash and the item/block total included (Java
  pauses an unloaded chunk's scheduled ticks, block entities and
  entities: `LevelChunkTicks` saves delays relative to game time and
  `SavedTick.unpack` re-bases them on load; and a save keeps all of
  them); for closed builds, a constant total. `persists` runs the same
  without the Java check, with accounting invariants where the build is
  random. Builds whose Java check waits on another track have both, so
  CI exercises unload and restart now.
- `CONTRAPTION_TRACE=<build name>` prints every run's per-tick trace
  (used to diagnose each failure below).
- `src/world/lighting.rs`: the flat test-column helpers
  (`flat_test_chunk`, `load_test_column`, `unload_test_column`) are now
  public outside `cfg(test)`, so integration tests can stream columns in
  and out without terrain generation. Nothing else in `src/` changed.

CI cost: the 15 non-ignored tests run in 1.4 s on Boat's 8 vCPUs;
everything including the ignored cases and the soak in about 4 s.

## Java sources

The official 26.3 server jar (bundler SHA-1
`33680f5f2ac32864d6d7cf5e56a705fdb3e05f4c`). Classes were decompiled with
Vineflower into a scratch folder outside the repo (nothing decompiled is
committed) and `Blocks` was read with `javap` from JDK 25:
`RedstoneTorchBlock`, `ObserverBlock`, `ComparatorBlock`, `DiodeBlock`,
`RepeaterBlock`, `RedstoneWireBlock`, `HopperBlockEntity`,
`PistonBaseBlock`, `SugarCaneBlock`, `StemBlock`, `KelpBlock`,
`GrowingPlantHeadBlock`, `CropBlock`, `FarmlandBlock`, `PumpkinBlock`,
`CrafterBlock`, `CrafterBlockEntity`, `DetectorRailBlock`,
`MinecartHopper`, `AbstractFurnaceBlockEntity`, `LevelTicks`,
`LevelChunkTicks`, `SavedTick`, and the `PushReaction` of `PUMPKIN`,
`MELON`, `CARVED_PUMPKIN`, `SUGAR_CANE`, `KELP` and `KELP_PLANT` in the
`Blocks` static initializer (all `POPPED`). The expectations below are
derived from those classes; none was measured in a running Java server,
so a derivation that misreads the tick order would show as a false
failure, and the integrator should treat a disagreement on timing as a
question, not a verdict.

Facts the derivations rest on:

- `LevelTicks.tick` moves a tick's due ticks into `toRunThisTick` (and out
  of the containers' `ticksPerPosition`) before running any; a running or
  about-to-run tick is not "scheduled" for `hasScheduledTick`.
  `LevelChunkTicks.schedule` keeps one tick per block type and position;
  a second is dropped.
- `ServerLevel.tick` runs scheduled block ticks, then block events, then
  entities, then block entities; a player's action is handled after the
  level tick, so it takes effect in the next one, and its neighbour
  updates run at once (`Level.updateNeighborsAt` calls
  `neighborChanged` synchronously on the six direct neighbours).
- `HopperBlockEntity.pushItemsTick` decrements the cooldown every tick
  before transferring; `tryMoveInItem` gives an emptied hopper cooldown
  `8 - k` (k = 1 if it already ticked this tick), so it pushes 7 ticks
  after the item arrived either way; `tryMoveItems` pushes then pulls in
  one cycle and sets cooldown 8.
- `RedstoneTorchBlock.RECENT_TOGGLES` is a per-level `WeakHashMap`, never
  saved; the eighth turn-off within 60 ticks burns the torch out and
  schedules a 160-tick restart (dropped if a tick is already scheduled).
- `PistonMovingBlockEntity` moves in 0.5 steps and lands on the third
  tick; a landing block goes through `Block.updateFromNeighbourShapes`,
  so a moved observer fires.

## Differences from Java found

Each is a reason a Java check is ignored; none was fixed here (all are in
other tracks' code).

1. **A player's edit reaches its neighbours a tick late** (Track A).
   VoxelCraft queues the neighbour updates of `set_block` and
   `use_redstone` to the next tick's drain, so the repeater loop lights at
   9 instead of 8 with a 19-tick pulse, and the burnout torch first turns
   off at 3 instead of 2.
2. **A tick due this tick counts as pending** (Track A). Java has drained
   it; VoxelCraft's `schedule_redstone` sees the position in `pending`
   and refuses. The observer clock runs at period 6 instead of 4.
3. **Burnout restart and history** (Track A). Java drops the 160-tick
   restart when the torch's own update has already scheduled its 2-tick
   check, so a self-powering torch stays out; VoxelCraft relights it after
   160 ticks and keeps relighting. Java doesn't save the toggle history;
   VoxelCraft does.
4. **Neighbour updates reach a two-block neighbourhood** (Track A). The
   BUD switch's piston extends as soon as the redstone block is placed.
5. **A 2-tick observer pulse doesn't turn a torch off** (Track A). In
   Java the torch's tick, scheduled during the observer's on-tick, runs
   before the observer's off-tick; VoxelCraft delivers the update a tick
   late and the torch sees no power.
6. **Hopper-to-hopper hop is 8 ticks, not 7, and an unlocked hopper
   waits a tick** (Track C2 for the transfer timing, Track A for the
   tick order). Together they give the hopper clock period 13 instead of
   11. The 8-tick hop also makes a hopper line fed every 8 ticks keep a
   buffered item whose successors leave the tick they arrive, so the
   sorter's filter hopper never sees them: 4 of 10 iron sorted and 5
   strayed to the junk chest. Nothing was lost or duplicated (the
   closed total held).
7. **Pistons don't move slime assemblies, and a moved observer doesn't
   fire on landing** (Track B). The flying machine never moves.
8. **A block a piston destroys doesn't update its neighbours** (Track B).
   The sugar cane above the broken block floats and the farm jams after
   one harvest.
9. **Pumpkins move instead of popping** (Track B). Java 26.3 registers
   pumpkins, melons and carved pumpkins with `PushReaction.POPPED`;
   VoxelCraft moves them (`automation::piston_reaction`), so the pumpkin
   would be pushed into the stem's cell. (VoxelCraft's sugar cane and kelp
   already pop.) Not yet observed in the corpus: in the headless world the
   age-7 stem grew no pumpkin in 2000 ticks at random tick speed 1024,
   where Java expects about ten (`StemBlock.randomTick`: 1 in 13 on dry
   farmland, then a free side). This is undiagnosed; the stem's growth
   light (`World::growth_light`) in the flat test world is the first
   thing to check, before blaming the stem rule. It was the light: see the
   [farms follow-up](#farms-follow-up-2026-11-23).
10. **Rails can't stand on hoppers, and a hopper under a cart unloads
    every 16 ticks** (Track D1). Java's rail needs a rigid top face, which
    the hopper's rim provides; VoxelCraft pops the rail into an item (the
    unloader then collects it, so the chest ends with 11 items: the ten
    ingots and the rail, not a duplicate). Java's hopper pushes and pulls
    in one 8-tick cycle; VoxelCraft drains the cart every 16 ticks.
    Fixed by the [Track D1 follow-up](#track-d1-follow-up-2026-11-23).
11. **Sugar cane grows four times too fast** (no v0.17 track). Java needs
    16 random ticks per block (AGE); VoxelCraft grows with chance 1/4 per
    random tick (`world::growth::tick_cane`). This is from reading the
    code: the rate test can't measure it yet, because the farm jams after
    its first harvest (item 8), so only 3 blocks grew in 4000 ticks.
    Fixed by the [farms follow-up](#farms-follow-up-2026-11-23).
12. **No crafter** (Track C1). Fixed: see the [Track C1 follow-up](#track-c1-follow-up-2026-11-23).

## Track A follow-up (2026-11-23)

After the merge, Track A (`v017-a-fixes`,
[update order record](2026-11-23-v0.17-update-order.md#follow-up-after-the-merge-2026-11-23))
fixed the two persistence failures it caused: chunk loads no longer
re-evaluate components (a BUD fired and a burned-out torch relit after a
reload), and the torch toggle history is no longer saved. Differences 1-4
above are gone; `player_actions_take_effect_at_once`, the burnout checks,
the BUD switch and the observer clock pass and are no longer ignored.

Two Java expectations above were wrong. Both were checked on the vanilla
26.3 server (the pinned jar, run headless with `/tick freeze`,
`/setblock` and `/tick step 1`):

- **The observer clock runs at period 6, not 4.** Once running, A was on at
  ticks 8-9 and 14, B at 6-7 and 12-13: each on 2 and off 4 ticks.
  `ObserverBlock.tick` sets the powered state, which schedules the other
  observer through its shape update, before it schedules its own
  off-tick, so the other observer's tick runs first.
- **A redstone torch never sees a 2-tick observer pulse** (difference 5).
  With observer, stone and wall torch in a row, the torch stayed lit
  through every pulse, for the same reason: the observer's off-tick runs
  before the torch's tick. The T flip-flop as built doesn't toggle in Java
  either; it needs a longer pulse, which is a redesign for Track F.

## Track C1 follow-up (2026-11-23)

After the merge, `crafter_autocrafts` failed at tick 79 ("ingots don't add
up to 27"). The build was wrong, not the crafter: `crafter_facing_east()`
looked the crafter up with `Block::from_name("crafter")`, which gives the
item's default state, `north_up`. That crafter put its first iron block
out of its north face as a dropped item, which no probe counts, instead
of into the chest east of it. Track C1 (`v017-c1-autocrafter`) replaced
the lookup with the `east_up` state, `crafter::encode` with
`orientation_of(+X, +Y)` (the slots are chest-backed, so `contents` and
the probes needed no change), and un-ignored the test.

Track F's expectation was then measured on the pinned 26.3 server with
`tools/java_autocrafter_trace.py`: headless, superflat, `/tick freeze`,
the build placed with `/setblock` in the same order, the top chest filled
with `/item replace`, then `/tick step 1` and the four probes read with
`/data get block` each tick for 320 ticks (with
`pause-when-empty-seconds=0`, or the empty server pauses after a minute).
Java makes the iron blocks at ticks 79, 151 and 223, conserves the 27
ingots on every tick, and all four probes equal VoxelCraft's tick for
tick over the whole run. The check now asserts those three ticks rather
than only their spacing. Hopper timing played no part: with Track C2's
container sides and the current hopper scheduling, the trace already
matches.

Normal tests (15): `repeater_loop_clock`, `comparator_subtraction_clock`,
`piston_door_2x2`, `piston_door_3x3`, `auto_smelter_smelts` (Java and
persistence), and the persistence tests of the observer clock, hopper
clock, torch burnout, flying machine, item sorter, sugar cane farm,
pumpkin farm, minecart line, BUD switch and T flip-flop. Ignored (15):
the Java checks above, `player_actions_take_effect_at_once`, the cane
growth rate, the crafter, and `soak_long_runs` (clocks and the cane farm
at ten times the length, persistence only).

Every persistence test holds: in every build VoxelCraft today resumes
after an unload exactly where it stopped, comes back from a save
identical tick for tick (pending ticks, hopper cooldowns, moving pistons,
carts and loose items included), and loses or duplicates nothing.

## Farms follow-up (2026-11-23)

On `v017-farms` (from `v017-redstone-automation` at `d71913f`), the two
growth checks no track owned: `sugar_cane_grows_at_java_rate` and
`pumpkin_farm_harvests` now pass and are no longer ignored. Neither
build's Java expectation changed: both were right.

**Java evidence.** The pinned 26.3 jar's bytecode (`javap` on Boat) for
`SugarCaneBlock`, `CactusBlock`, `StemBlock`, `CropBlock.getGrowthSpeed`
and `BambooStalkBlock`. The new `tools/extract_java_growth_fixtures.py`
reads each method's numeric constants in bytecode order, fails unless they
have the shape read here, and writes `tests/fixtures/java/26.3/growth.json`;
`world::sugar_cane`'s `growth_constants_match_java` test pins VoxelCraft's
constants to it.

**Pumpkin farm: a harness gap, not the stem.** VoxelCraft's
`tick_stem` matches `StemBlock.randomTick` step for step (raw brightness
at least 9 at the stem, one in `(int) (25 / getGrowthSpeed) + 1`, age 7
picks a random side, fruit into air over `supports_stem_fruit`).
`World::sky_light` is exact (`Some`) only where a column and its eight
neighbours are loaded and lit, and the rig loaded only the build's own
column, so `growth_light` fell back to block light, 0, and the stem never
grew. In play the player's surroundings are always loaded, so the game
was never affected. The rig (`tests/contraptions/rig.rs`) now also loads
the ring of columns around a build as empty air (uniform chunks get no
random ticks, so no build's random sequence changes) and keeps it loaded
while the build's own columns unload and reload. The farm now grows 8 or
9 pumpkins in 2000 ticks at speed 1024 (the plain run and each cut run).
Java: dry farmland under the stem and none around it give growth speed 2,
so one in 13 per random tick, then one side in four is free: at 0.25
random ticks per block per tick, a pumpkin every 208 ticks, about 9.6.

**Sugar cane: a game bug, now fixed.** Java's `SugarCaneBlock.randomTick`,
with air above and a stalk shorter than 3, raises `AGE` (0–15) by one,
and at 15 places a cane above and resets its own age to 0, so a block
grows after exactly 16 random ticks. The age changes use
`setBlock(..., 260)` (`UPDATE_INVISIBLE | UPDATE_SKIP_BLOCK_ENTITY_SIDEEFFECTS`):
no neighbour updates, but shape updates go out, so an observer facing the
cane fires on every step. `randomTick` doesn't check water (`canSurvive`
does, on shape updates). VoxelCraft had no age: it grew with chance 1/4
per random tick (four times as fast, 228 blocks here) and checked water.
The new `world::sugar_cane` adds `AGE` 1–15 as states 13953–13967 (age 0
stays 92; [architecture](../architecture.md#integrator-allocation-sugar-cane-age)),
each answering as sugar cane for its properties, name, drops and
pick-block, and ports `randomTick` with those flags (VoxelCraft's flag 0:
shape updates only). Placement still needs water beside the soil. The
farm now grows 61 blocks in 4000 ticks (Java about 62); its observer
faces the third block's cell, which the second block's ages don't touch.
The farm's checks read every age as cane.

**Cactus: not grown at all, left as a gap.** Java's `CactusBlock` shares
the age logic (`AGE` 0–15, a new cactus at 15 below height 3, a cactus
flower at age 8 with chance 0.25 in a stalk of 3, else 0.1, flags 260)
and breaks a cactus beside a solid block or lava. VoxelCraft's cactus is

## Track F follow-up: the T flip-flop (2026-11-23)

On `v017-f-flipflop` (from `v017-redstone-automation` at `d71913f`).
Track A found on the vanilla server that the original build never
toggles: a redstone torch never sees a bare 2-tick observer pulse.
The redesign keeps the hopper pair, the torch lock and the comparator
lamp, and puts a delay-2 repeater between the observer and the torch's
block. The repeater stretches the 2-tick pulse to 4 ticks: long enough
for the torch, and shorter than the 7 ticks before the receiving hopper
can push back (`HopperBlockEntity`: an emptied receiver gets cooldown
`8 - k` and counts its first tick down). So each pulse moves the diamond
across exactly once. The two-dropper flip-flop was considered and
rejected: both droppers fire on the same pulse, and whichever holds the
item last sends it back, so it never toggles.

Java evidence: `tools/java_server_trace.py` (Track C2's tool, copied in
with an optional per-tick `script` for the input changes) ran
`tests/contraptions/java/t_flip_flop.json` on the pinned server (SHA-1
`33680f5f2ac32864d6d7cf5e56a705fdb3e05f4c`, OpenJDK 25, headless on a Boat
sandbox) for 130 ticks, with input changes before ticks 10, 40, 70 and
100. Per pulse:

| Ticks after the input change | What happens |
|---|---|
| +1 to +2 | The observer is on |
| +5 to +8 | The repeater is on |
| +7 to +10 | The torch is off, unlocking both hoppers |
| +7 | The diamond crosses |
| +9 / +13 | The lamp lights (diamond arrived) / goes dark (diamond left) |

The diamond crossed at 17, 47, 77 and 107; the lamp was lit 19-52 and
79-112. `/setblock` fires an observer once (`BlockInput.place` calls
`Block.updateFromNeighbourShapes`), which a player's placement doesn't.
The spec therefore places the repeater by script at tick 5, after that
stray pulse (ticks 2-3) has gone into empty air, and the VoxelCraft build
does the same. Its check compares every tick of the diamond, lamp, torch,
repeater and observer against this timeline, ignoring the observer
before tick 5.

VoxelCraft today matches through tick 16. At tick 17 the torch goes off
on time, but the unlocked hopper pushes a tick later: hoppers are still
scheduled ticks on this branch. With Track C2's hopper ticker
(`origin/v017-c2-hoppers`, hoppers as block entities after block events)
merged onto this branch for a scratch check, `t_flip_flop_toggles`
passed every tick, through the unload, restart and mid-motion restart
cuts. The test is no longer ignored and fails on this branch until that
merge, like the other hopper builds. No redstone component was changed;
the fault is the hopper timing that C2 already fixes.

Checks on this branch (stock `scripts/boat-check.sh`): `cargo clippy
--profile ci --locked --all-targets -- -D warnings` clean; `--test
contraptions -- --include-ignored` 24 passed, 5 failed (the three hopper
builds that wait for C2's ticker: `hopper_clock_period`,
`item_sorter_filters`, `t_flip_flop_toggles`; and `pumpkin_farm_harvests`
