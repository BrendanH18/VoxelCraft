## What was built

- `world::piston` (new): `reaction` (Java push reaction, block entity and
  unbreakable flags per state, and `isPushable`), `resolver` (an original
  port of `PistonStructureResolver`'s rules, including the reorder at a
  collision and Java's direction order for branches), `events` (the piston
  block-event queue, `checkIfExtend`, `triggerEvent` and `moveBlocks`),
  `moving` (the moving block entity, its tick and `finalTick`, collision,
  rendering and saves) and `entities` (push records and the shared body
  push).
- `moving_piston` is registered (`Block::from_name("moving piston")`) and
  removed from `registry_gaps.json`. It stays one chunk state (1470); its
  `facing` and `type` come from the block entity (`World::moving_piston_state`).
- The moving-block ticks run after block events (`World::tick_moving_pistons`,
  from `tick_redstone` and `simulation::tick_world_rules`);
  `ServerLevel.handlingTick` is modelled for the drop check. See
  [Integration](#integration-with-the-v017-tree) for the block-event queue.
- Physics: `BlockSource::moving_boxes` lets moving blocks collide with their
  progress-offset shape in every collision query, including from a
  neighbouring cell; `physics::block_collision_boxes` gives a block's
  standalone shape.
- Entity pushes are applied after the world tick to the host, controller
  and CLI-agent players (`piston::push_player`), and through
  `Entities::apply_piston_pushes` to mobs, items, orbs, minecarts/boats and
  primed TNT; the headless LAN host does the same.
- Explosions and other drops of a moving cell give its moved block.
- Observers see cells becoming or leaving `moving_piston` through the
  shape updates the moves send.
- Saves: the `automation` property is `v2` with `M` (block entity,
  progress, previous progress, ticked-this-tick) records; queued piston
  events are block events in the `redstone` property; `v1` `m` records migrate (installed cells become block entities;
  the drawn-only retracting head is dropped, as v1 had already placed the
  base).

## Integration with the v0.17 tree

Merged onto `origin/v017-redstone-automation` (`30800fd`, tracks A, C1, C2,
D1, D2, E1, E2, F and G) as `v017-b-integrated`:

- **One block-event queue.** The branch's own piston queue is gone.
  `checkIfExtend` (`World::check_piston`, from Track A's `onPlace` and
  neighbour updates) queues `World::queue_block_event(pos, piston, b0,
  get3DDataValue)` with the resolver pre-check and the `TRIGGER_DROP` (2)
  rule; Track A's `run_block_events` (Java's dedup, end-of-tick order,
  waiting in non-ticking cells, saved as `redstone` `e` records) dispatches
  through `trigger_block_event` and its `doBlockEvent` check to
  `World::piston_trigger_event`, now the port of `triggerEvent`. The
  `PISTON_*` constants match. Track A's batch around piston events is
  removed: the moves are ported Java.
- **Java's `setBlock` flags and updates.** Moves use `set_block_flags` /
  `edit_exact_flags` with Java's values: 324 for cells set moving, 18 for
  destroyed blocks, 82 for vacated cells (in `HashMap` bucket order, then
  their shape updates), 276 for the retracting base and the arm removed
  before a pull, 67 for the extended base and landed blocks (then
  `neighborChanged`), 3 for `removeBlock` and `finalTick`, and 2 for a
  retraction that found power. Then `moveBlocks`' explicit updates:
  `affectNeighborsAfterRemoval` and `updateNeighborsAt` for destroyed blocks,
  `updateNeighborsAt` for each pushed block's old cell and the arm, and the
  retracting base's `updateNeighborsAt` and shape updates. Track A's
  update stack orders all of them.
- **Heads** follow `PistonHeadBlock.updateShape` (a head whose base side
  changed and can't survive breaks) and `affectNeighborsAfterRemoval` (a
  removed head destroys its fitting extended base, with drops) in Track
  A's dispatch (`redstone_shape_update`, `affect_neighbors_after_removal`).
  Observers' `onPlace` is Track A's.
- **Tick phase.** `tick_moving_pistons` runs after `run_block_events` in
  `tick_redstone` and `tick_world_rules`, closing Track A's difference that
  moves finished at the start of the next tick, and its piston difference 9
  (no resolver pre-check, no `TRIGGER_DROP`, retry while moving).
- **Track E1's game events** stay with the moves: `block_activate` (the
  extended base) on extension, `block_deactivate` (the moving piston) on
  retraction, `block_destroy` (the block) for each block a move destroys.
- **Landing.** A landed (or `finalTick`ed) block then runs its own
  `updateShape` from each side (the rest of `updateFromNeighbourShapes`),
  so a moved observer fires on landing and an unsupported attached block
  breaks. Cells a move destroys, vacates or fills, and landed cells, then
  run VoxelCraft's `settle` (cane, sand and plant support), which stands
  in for the `updateShape` of blocks Track A doesn't dispatch.
- **Rendering and counts.** `moving_piston_blocks` gives each moving cell's
  block (a retracting base stays in its cell as an extended base);
  `moving_piston_heads` gives the heads sliding home.
- **Contraptions (Track F).** `flying_machine_travels` and
  `sugar_cane_farm_harvests` now pass and are no longer ignored; the
  flying machine also survives unload and restart. With
  `--include-ignored`, the remaining failures are not pistons':

## Differences from Java

- Entity pushes are recorded during each moving-block tick and applied after
  the world tick, before mobs move, instead of inside each block entity's
  tick after entities moved. The per-entity order of pushes matches, but an
  entity's collision during a push sees every moving block already advanced.
- `Entity.move(PISTON)` is modelled without step-up, `applyEffectsFromBlocks`
  and the `onGround` update.
- The piston head's short arm (`SHORT`) is not modelled; heads use one shape.
- Honey's `isSupportedBy(pos)` is approximated by the entity's feet being on
  the moving cell's top.
- Projectiles, falling blocks, End crystals and decorations (item frames,
  paintings, armor stands) are not pushed. Java pushes them and breaks
  hanging entities.
- `MovingPistonBlock.destroy` (removing an extended base behind a moving
  cell a player breaks) is not modelled: a moving cell has no outline, so
  only explosions and edits remove it, which in Java don't call it either.
- Saves keep the current progress and the previous tick's, so a reload
  continues exactly; Java saves only the previous progress and replays one
  step.
- A push that reaches an unloaded cell is refused; Java's server would load
  the chunk.
- The moving-piston state is one chunk state; Java's `facing`/`type`
  properties are derived from the block entity.
- LAN clients don't receive moving-block entities (they didn't receive the
  old motion records either), so a client sees a moving cell as empty and
  without collision for its two ticks; the host simulates pushes.
