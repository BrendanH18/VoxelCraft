## What was built

- `world::piston` (new): `reaction` (Java push reaction, block entity and
  unbreakable flags per state, and `isPushable`), `resolver` (an original
  port of `PistonStructureResolver`'s rules, including the reorder at a
  collision and Java's direction order for branches), `events` (the piston
  block-event queue, `checkIfExtend`, `triggerEvent` and `moveBlocks`),
  `moving` (the moving block entity, its tick and `finalTick`, collision,
  rendering and saves) and `entities` (push records and the shared body
  push).
- `moving_piston` is registered (`Block::from_name("moving piston")`) and
  removed from `registry_gaps.json`. It stays one chunk state (1470); its
  `facing` and `type` come from the block entity (`World::moving_piston_state`).
- `tick_redstone` now runs scheduled ticks, then piston block events, then
  the moving-block ticks (landing neighbour updates drain at once);
  `ServerLevel.handlingTick` is modelled for the drop check.
- Physics: `BlockSource::moving_boxes` lets moving blocks collide with their
  progress-offset shape in every collision query, including from a
  neighbouring cell; `physics::block_collision_boxes` gives a block's
  standalone shape.
- Entity pushes are applied after the world tick to the host, controller
  and CLI-agent players (`piston::push_player`), and through
  `Entities::apply_piston_pushes` to mobs, items, orbs, minecarts/boats and
  primed TNT; the headless LAN host does the same.
- Explosions and other drops of a moving cell give its moved block.
- Observers: cells becoming or leaving `moving_piston` are state changes they
  see; a powered observer placed with no pending tick turns off.
- Saves: the `automation` property is `v2` with `M` (block entity,
  progress, previous progress, ticked-this-tick) and `B` (queued event)
  records; `v1` `m` records migrate (installed cells become block entities;
  the drawn-only retracting head is dropped, as v1 had already placed the
  base).

## Differences from Java

- Block events and neighbour updates still use VoxelCraft's redstone update
  order; Track A is replacing it with a Java-style queue. The seam is
  `World::queue_piston_event` (Java `level.blockEvent`) and
  `World::piston_trigger_event` (Java `doBlockEvent`), with
  `run_piston_block_events` standing in for `runBlockEvents` until then.
- Entity pushes are recorded during each moving-block tick and applied after
  the world tick, before mobs move, instead of inside each block entity's
  tick after entities moved. The per-entity order of pushes matches, but an
  entity's collision during a push sees every moving block already advanced.
- `Entity.move(PISTON)` is modelled without step-up, `applyEffectsFromBlocks`
  and the `onGround` update.
- The piston head's short arm (`SHORT`) is not modelled; heads use one shape.
- Honey's `isSupportedBy(pos)` is approximated by the entity's feet being on
  the moving cell's top.
- Projectiles, falling blocks, End crystals and decorations (item frames,
  paintings, armor stands) are not pushed. Java pushes them and breaks
  hanging entities.
- `MovingPistonBlock.destroy` (removing an extended base behind a moving
  cell a player breaks) is not modelled: a moving cell has no outline, so
  only explosions and edits remove it, which in Java don't call it either.
- Saves keep the current progress and the previous tick's, so a reload
  continues exactly; Java saves only the previous progress and replays one
  step.
- A push that reaches an unloaded cell is refused; Java's server would load
  the chunk.
- The moving-piston state is one chunk state; Java's `facing`/`type`
  properties are derived from the block entity.
- LAN clients don't receive moving-block entities (they didn't receive the
  old motion records either), so a client sees a moving cell as empty and
  without collision for its two ticks; the host simulates pushes.
