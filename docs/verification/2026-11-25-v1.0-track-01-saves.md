# v1.0 Track 1: save compatibility — 2026-11-25

Status: **Implemented, unverified.** Nobody has played with it. Branched
from `3685593` (the v1.0 plan) as `v1.0/track-01-saves`. Rows: UX-05b (save
migration and a 1.0 save-compatibility policy) and UX-04a (install, start,
save, quit and reopen on supported platforms). Track 1 of the
[v1.0 plan](../roadmap.md#v10-plan-2026-11-25).

## What changed

- **The policy**, [saves.md](../saves.md): which saves 1.0 opens (every
  tagged release from v0.8.0 to v0.18, and 1.0's own), how loading migrates
  chunks, level files and options, what happens to unknown block states,
  items, mobs, level keys and chunk formats, how worlds are backed up, how
  each kind of interrupted or damaged save is recovered, what may never
  change after 1.0, and which platform checks are automated. Linked from the
  [documentation index](../README.md) and
  [releases](../releases.md#player-data-and-old-saves).
- **Save fixtures from every tagged release** in
  `tests/fixtures/saves/<tag>/`, each made by that tag's own game on Boat
  (see [the fixtures](#the-fixtures)).
- **`level.txt_old`** (`world::storage`): every write of a level file is
  Java's `LevelStorageAccess.saveLevelData` with `Util.safeReplaceFile`: the
  new text goes to `level.txt.tmp`, the current file becomes `level.txt_old`
  (replacing the previous one), the new file takes its place, and a failed
  last rename moves the old file back. `Storage::exists` is Java's
  `hasWorldData` (`level.txt` or `level.txt_old`), so a world caught between
  the renames is still a world.
- **Unreadable level files are detected**: a missing (`level.txt is
  missing`), empty or cut-off file (no final newline; every writer ends each
  line with one) is an error, as an unparseable seed already was. Before,
  a level file cut off between lines loaded with whatever keys it still had.
- **Java's recovery screen** (`app::title::recover`, Java's
  `RecoverWorldDataScreen`): "Failed to load world", the folder, a state
  line for `level.txt` and for `level.txt_old` (when it was written, then
  "No issues", "Missing file" or the error, in green or red), **Attempt to
  Restore** (enabled when the level file is unreadable and its kept copy
  reads; otherwise the tooltip "No state to recover from available") and
  **Back**. Restoring backs the world up first (the existing backup screen),
  then `Storage::restore_level_from_old` (Java's `restoreLevelDataFromOld`:
  the unreadable file to `level.txt_corrupted_<yyyy-MM-dd_HH.mm.ss>`, the
  kept copy into place), then "Recovery done" with "Recovery was
  successful!" and **Continue** (opens the world) / **Back**, or "Failed to
  recover from previous state." Select World shows an unreadable world as
  Java's `CorruptedLevelSummary` does: "Failed to load world summary", its
  primary button **Attempt to Recover** (enabled; it was disabled), Edit and
  Re-Create disabled. Opening a world with `--world` whose level file is
  unreadable shows the same screen over Select World instead of the old
  notice.
- **Saved chunks without a level file** (`Storage::has_chunks_without_level`)
  are listed as unreadable and refused, where before the folder was hidden
  and `--world` would have started a new world and saved over its chunks.
- **Damaged `chunks.bin`** (`Storage::load_chunks_recovering`, used by every
  dimension load): every intact chunk record loads, a record whose runs
  don't make a chunk is skipped, reading stops where the file is cut off,
  and the lost chunks regenerate, as Java's `ChunkMap` and `IOWorker` log a
  chunk they fail to read ("Failed to read chunk") and generate it again.
  The damaged file is first copied, untouched, to
  `chunks.bin.damaged-<secs>`. Before, any damage threw the whole file away
  for the session and the next save replaced it with only the chunks
  changed since. A file whose header isn't a `VXC` format at all is now
  damage too; only a `VXC` header with an unknown version is kept aside as a
  newer build's (`chunks.bin.unknown-<secs>`, unchanged).
- **Damaged Nether and End level files** (`app::dimension::load_dimension`):
  the dimension's `level.txt_old` is used and the damaged file is kept as
  `level.txt.damaged-<secs>`; with no kept copy the chunks still load and
  the dimension's containers and entities are reported lost. Before, the
  dimension silently loaded with no containers or entities and the next
  save wrote that.
- **The player is told** (`Game::report_load_damage`): the full notice in
  chat, and "Part of this world's save was damaged; open chat for details"
  on the action bar, when a world opens or the player changes dimension.
- **UX-04a on Linux**: `tools/save_fixtures/cycle-current.sh` builds this
  tree on Boat, runs the fixture run on it (start, build and save a world,
  close the window, reopen, close again), collects it and runs the ignored
  test `live_run_of_this_build_starts_saves_quits_and_reopens` on it.

### Java sources

Read on Boat from the pinned client jar (SHA-1 `e877b6a0…`,
`CLIENT_SHA1` in `tools/extract_java_registry_names.py`), decompiled with
Vineflower 1.11.1 into a scratch folder; nothing is copied.
`RecoverWorldDataScreen` (layout, which states are listed, when the restore
is enabled, the backup before restoring, the done screens);
`WorldOpenFlows.openWorldLoadLevelData` (the screen opens when the level
file can't be read; Continue opens the world again);
`LevelStorageSource` (`findLevelCandidates` and `hasWorldData` count
`level.dat_old`; `saveLevelData`; `restoreLevelDataFromOld` and
`corruptedDataFile`; `getFileModificationTime` falls back to the old file);
`LevelSummary.CorruptedLevelSummary` (not disabled, primary action
`recover_world.button`, can't edit or re-create); `Util.safeReplaceFile`,
`safeReplaceOrMoveFile` and the file-name date format; `ChunkMap` and
`IOWorker` ("Failed to read chunk"); `SerializableChunkData` (sections
decoded with `promotePartial`, "Recoverable errors when loading section");
`ItemStack.OPTIONAL_CODEC`; `EntityType` ("Skipping Entity with id");
`assets/minecraft/lang/en_us.json` (`recover_world.*`).

### Differences from Java

- Java's **Report a Bug** button is left out; there is no public tracker
  to send players to.
- Each state line is one colour; Java greys the date inside it.
- The `_corrupted_` date is UTC, like the game's backup folders; Java uses
  local time.
- A block state id the build doesn't register is kept (an invisible,
  non-solid placeholder written back unchanged) where Java's section codec
  replaces what it can't decode. This was already the game's behaviour; see
  [open decisions](#open-decisions).
- Java regenerates a bad chunk silently apart from its log; the game also
  tells the player and keeps a copy of the damaged file.

## Remaining gaps

- The owner's play: the recovery screen and the damage notices have only
  been driven by tests; the screen has no capture.
- The Mac and Windows install, save, quit and reopen runs (UX-04a), and
  updating a real install (UX-04b).
- The fixtures cover the overworld only; Nether and End saves are covered
  by unit tests, not by a release's own save.
- Worlds from v0.7.0 and earlier have no fixture.
- Files are not flushed to disk before the renames, as Java doesn't flush
  `level.dat`; a power cut can still leave a short file, which the recovery
  handles.
- `options.txt` is written in place, not through a temporary file; a write
  cut off leaves the options it reached and defaults for the rest.

## Open decisions

- **Unknown block states.** The game keeps a block state id it doesn't
  register as an invisible, non-solid placeholder and writes it back
  unchanged, so a newer build's block survives a round trip through an
  older one; Java's section codec replaces what it can't decode. This was
  the existing behaviour, and it matters only for downgrades, which ask for
  a backup first. Track 1 kept it and documented it rather than change
  what saves already do; the Java-faithful alternative is to load such
  states as air.
- **Fixture trimming.** Each fixture keeps only its own two chunk records,
  not the 17–68 terrain chunks its run's simulation touched. Keeping them
  would grow the fixtures to up to 0.9 MB each.

## Region storage (2026-11-26, Track 1b)

Track 3b moved saves into region files (`region/r.<x>.<z>.vxr`,
[saves.md](../saves.md#region-files)), and this record's live cycle and
fixture tools still read `chunks.bin` (open item 4 of the
[Track 3b record](2026-11-26-v1.0-track-03b-region-storage.md#6-remaining-gaps-and-open-decisions)).
Branch `v1.0/track-01b-save-cycle`, from `f6c397a`, by Claude Opus 5.5 as
the Track 1b implementation agent. Status: **implemented, unverified**, as
for the rest of this record; nobody played the game.

What changed:

- **A stable log line.** Opening a dimension's region files logs
  `region storage: N chunk records in the overworld`, N being the records
  their tables name (`app::dimension::attach_regions`). The save line
  (`saved N overworld chunk records to … written)`) was already there.
- **`make-fixture.sh` and `trim_regions.py`.** A world with `region/` is
  trimmed by the new `trim_regions.py`, as `trim_chunks.py` trims
  `chunks.bin`: it keeps chunk row 4's records, each frame copied byte for
  byte into the same table slot of a new file laid out as the game lays
  one out, and prints `kept total` in records.
- **`collect.py`** copies the whole world folder (`level.txt`, and from 1.0
  `region/` and `level.txt_old` when there is one). For a region world the
  manifest's `create_saved_chunks` is the records on disk after the first
  run (trim's total), `create_save_records` the records the first run's
  waited save wrote, `reopen_loaded_chunks` the reopen's `region storage`
  line and `reopen_saved_chunks` the reopen's save line; `chunks.kept` is
  the kept records that hold blocks. The pre-1.0 log lines are still read
  when the new ones are absent, so a tag's run collects as before.
- **`tests/save_compat.rs`.** Worlds are copied with their subfolders.
  `check_opens` reads blocks from `chunks.bin` and then the region records
  (records win, as in the game); a world whose level file has
  `region_chunks` is opened read-only with region storage, the columns
  around the build loaded, and its chest and entities checked there.
  `check_migrates` became `check_region_save`: open with region storage,
  save as the game does with nothing loaded, reopen from the records; the
  migration's assertions (`chunks.bin` moved to an unchanged
  `chunks.bin_old`, the stored entities) apply when the world had a
  `chunks.bin`. The live-run test calls it instead of `check_resaves`,
  whose `Storage::save` writes `chunks.bin`, for a region world. The
  release fixtures v0.8.0–v0.18 are unchanged and take the same paths as
  before.

The cycle, `scripts/boat-check.sh -- 'cargo clippy --profile ci --locked
--bin voxelcraft --test save_compat -- -D warnings && cargo test --profile
ci --locked --test save_compat --test save_interrupted && bash
tools/save_fixtures/cycle-current.sh'`, ran twice, both exit 0: once on
the code, then on the final tree (after `cycle-current.sh` learned to print
the manifest's counts and the docs changed). The final run:

- clippy clean; `save_compat` 4 passed, 1 ignored (the live run);
  `save_interrupted` 10 passed;
- the live run placed 101 blocks, the agent reached the chest (yaw 90) and
  both runs exited 0 after their windows were closed;
- the first run's save on quit wrote 60 records; the reopen found all 60
  (`region storage: 60 chunk records in the overworld`) and its save on
  quit wrote 18 (the first run: 59, 59 and 22, its save 12.1 ms on the
  main thread; the simulation touches a slightly different set of terrain
  chunks each run);
- trimmed to chunk row 4, the world kept 2 of 60 records, both with blocks,
  in two region files (40,960 bytes each in the first run) beside `level.txt`
  (163,832 bytes in all with the manifest and options);
- `live_run_of_this_build_starts_saves_quits_and_reopens` passed, with the
  daylight detector placed as state 1281 saved as 1293 (its power follows
  the sun, as for the releases).

Still open: 1.0's own checked-in fixture isn't made (it is made from the
release commit); the trimmed fixture's two region files are mostly table
(36 KB of header each), which is the format's and fine for its size; Mac
and Windows runs stay with the owner.
