Branch `v1.0/track-03b-region-storage`, from `c257e6f` (every other v1.0
track merged), built by Claude Opus 5.5 as the Track 3b implementation
agent after the owner's decision of 2026-11-26: Track 3's 4-hour soak found
memory growing about 450 MB an hour in fast travel, because every modified
chunk, its block entities and its stored entities stayed in memory for the
session, and every autosave rewrote all of them on the main thread (2.2 s
after 4 hours). The fix the owner chose is Java's: write a chunk with
everything it owns when it unloads, read it back when it loads, and make
autosave incremental and off the main thread.

## 1. What changed

### Region files (`world::region`)

- **Files.** Each dimension folder gets `region/r.<x>.<z>.vxr`, one file per
  16 x 16 columns of 32-block chunks: the 512 x 512 blocks a Java region
  covers. A file has a slot for each chunk of its columns, 16 rows (512
  blocks of height; the Overworld's 12 rows, the Nether's and End's 8 fit).
  It is a magic sector (`VXREGION`, file version 1), a table of 4096 entries
  (each the record's first 4096-byte sector and its byte length) and the
  records in sectors. [saves.md](../saves.md#region-files) has the layout.
- **Records.** `VXK1`, the payload length, an FNV-1a 64-bit checksum and the
  payload. Payload version 1 holds the chunk's position (checked on read),
  its blocks if the player changed them (the `chunks.bin` `VXC4` runs), its
  block entities as the level file's own keys and texts, its water, lava and
  bubble-column cells, its fire cells with their remaining delays, and its
  entity batches (each a list of the level file's entity keys).
- **Writing**, as Java's `RegionFile.write`: a new record goes into the first
  run of free sectors (or the end), its table entry is then written, and only
  then are its old sectors free. Rewriting one chunk touches only its own
  sectors and entry. A file whose table had damage dropped rewrites the
  whole table at its next write.
- **The store** (`RegionStore`, Java's `RegionFileStorage` and `IOWorker`):
  - the game queues a `Patch` per chunk (blocks, state, entities, each kept
    or replaced, and entity batches to append); patches to one chunk merge
    while they wait;
  - an I/O thread, `region-io`, takes everything queued, writes it region by
    region, then runs the work waiting for it (the level files);
  - reads apply every queued patch to what is on disk, so a chunk that
    unloads and loads again at once gets what it just wrote; the files
    lock is taken before the queue lock everywhere, so a patch is either
    still queued or on disk, never both;
  - at most 4096 chunks wait (`MAX_PENDING`); past that, queueing waits for
    the disk;
  - at most 64 files stay open;
  - dropping the store writes everything queued, then ends the thread;
  - a store opened read-only (scripted runs) never writes, copies or repairs
    anything.
- **Damage.** Opening a store checks every region file's table: entries
  that point past the end of the file or overlap another record are dropped,
  the file is copied to `r.<x>.<z>.vxr.damaged-<secs>` and the damage is
  returned for the player ("Some of the nether's saved chunks in r.0.0.vxr
  couldn't be read (it is cut off): 1 of 2 were kept and the rest
  regenerate. The damaged file was kept as …"). A record that fails its
  checksum, its length, its position or its decoding when it is read is
  dropped from the table, the file is copied aside once, the chunk
  regenerates and the player is told, as Java's `ChunkMap` logs "Failed to
  read chunk" and generates it again.

### Unload and load (`world::chunk_records`)

- **Unloading** (`World::evict_chunks`, called by streaming's `recenter` for
  every chunk it unloads, before any is removed): live falling blocks are
  stored, then each chunk's state is taken out of the world's tables:
  - 19 block entity systems: brewing stands, furnaces, chests (and their
    transport identities), brushable blocks, jukeboxes, beehives (and
    released bees), creaking hearts, sculk, copper golem statue names, trial
    spawners and vaults, signs, shelves and chiseled bookshelves, spawners,
    campfires, decorated pots, dripstone drips and big dripleaf tilts,
    banners and lecterns, beacons, conduits, crafters, potent sulfur, and
    stored falling blocks;
  - each system's text is its own level file writer's, run on the chunk's
    entries alone (the chunk's entries are swapped in for the whole table),
    so a record holds exactly what the level file would and needs no new
    serializers;
  - water, lava and bubble-column cells (kept for chunks the player changed;
    generating a chunk again wakes its own, as before), and fire cells with
    their delays.

  The chunk's record is then queued whole: its blocks if changed, that
  state, and no entities. A chunk with nothing to keep and no record writes
  nothing. Its blocks no longer go into `World::saved`: with region storage
  that map only holds `chunks.bin` chunks not yet migrated.
- **Entities** (`entity::chunk_storage`): the entity pass stores the
  entities of unloaded chunks as before, then serializes each such chunk's
  mobs, items, orbs, carts and boats, decorations, potion clouds and
  tridents through `Entities::save_props` (on a scratch `Entities`) into a
  batch appended to the chunk's record (Java's `EntityStorage.storeEntities`),
  and drops them. Arrows, thrown items, eyes, fireballs and primed TNT were
  never saved, so they wait in memory as before. A stored villager's bed and
  job claims, and a stored heart-bound creaking's uid, stay indexed so
  villages, raids, cats and creaking hearts keep treating them as present
  (Java keeps POI claims in its POI storage); the index is saved in the level
  file (`stored_index`), with the next mob and cart ids (`entity_ids`), so ids
  never repeat while stored entities wait on disk. Villagers, golems and
  trader llamas now save their uid (they used to get a new one at every
  load), so leads, seats and hearts that name them still find them.
- **Loading** (`Job::Load`, Java's `ChunkMap.scheduleChunkLoad`): the worker
  that would generate a chunk reads its record first. A record with blocks
  installs as a changed chunk (`World::insert_record`); otherwise the chunk
  generates and the record's state comes with it. `World::restore_record`
  runs once the chunk is in place, so the systems' readers see its blocks,
  and before its block entities register, so saved state wins over the
  generated loot, bees and trial configuration registration would create.
  Saved fire ticks are scheduled before the chunk's fires are scanned, so
  they keep their delays; fluid cells go back in the queues; entity batches
  go to the entity pass, which loads each as the level file would.
- `World::section_data` (portal and gateway searches) reads an unloaded
  changed chunk's blocks from its record.

### The level file and the records

The level file keeps its keys and still holds the state of the chunks that
were loaded when it was saved; a new key, `region_chunks`, lists those
chunks. Their records keep only their blocks: the rest is older than the
level file and is ignored when such a chunk loads, until it unloads and
writes its whole record. This keeps every save's level file and records
consistent without rewriting every loaded chunk's record at each autosave.
A level file without `region_chunks` (every world before 1.0) holds every
chunk's state until its first save. Other new keys: `fluid_ticks` (scheduled
fluid ticks of changed loaded chunks: fluid ticks now survive quitting, as
in Java), `stored_index` and `entity_ids` (above). Redstone and hopper
scheduling (`redstone`, `automation`) stay whole in the level file.

### Saving (`app::save`, `World::save_records`)

- **Autosave** (`Game::autosave`, every 5 minutes) queues only: the entities
  still waiting in memory for unloaded chunks, the state the level file held
  for chunks that aren't loaded (a world's first save moves it all), and the
  blocks of loaded chunks changed since their record was written. The level
  files (the dimension's, then the player's) are written by the I/O thread
  after every record queued before them, so a level file never names a
  record that isn't on disk; then a migrated `chunks.bin` moves aside. The
  main thread doesn't wait for any of it.
- **Quitting, changing dimension, `/save` and the LAN host's save**
  (`Game::save`) do the same and wait until all of it is written before the
  world closes.
- **Errors**: a write that fails on the I/O thread reaches the player as
  every failed save did ("Could not save the world: …", and the title
  screen's save error), checked each frame (`Game::poll_region_storage`),
  which also tells the player about chunks that couldn't be read.
- Scripted runs (screenshots, benchmarks) read region files but never write
  them; LAN clients have none.

### Migration

A world from v0.8.0 to v0.18 opens as before (`chunks.bin` and the level
file's per-position keys load into memory), with region storage attached and
the level file holding every chunk's state. Its first save moves every
`chunks.bin` chunk, every block entity of a chunk that isn't loaded and
every entity stored in one into region records, writes the level file with
only the loaded chunks' state and `region_chunks`, and then moves
`chunks.bin` to `chunks.bin_old` (kept unchanged); the replaced level file
is `level.txt_old` as for every save. A crash before that first save
completes leaves the world as the last save left it: region files beside a
`chunks.bin` and a level file without `region_chunks` are moved aside as
`region.unsaved-<secs>`. A `chunks.bin` chunk whose blocks already have a
record (a crash between the records and the rename) gives way to the
record. The backup policy is unchanged ([saves.md](../saves.md#backups)): the
updater's backup holds the world from before the update, and the replaced
files are kept beside it.

### Java sources

Decompiled on Boat (sandbox `voxelcraft-java-regionfile`, deleted) from the
pinned client jar (SHA-1 `e877b6a0…`, `CLIENT_SHA1` in
`tools/extract_java_registry_names.py`) with Vineflower 1.11.1 on JDK 21,
into the sandbox only; nothing was copied.

- `RegionFile`: 4096-byte sectors; an 8 KiB header of 1024 offsets (sector
  and count) and 1024 timestamps; at open, entries that point into the
  header, have no sectors or start past the file's end are dropped with a
  warning ("has an invalid sector … out of bounds"); `write` allocates
  free sectors, writes the chunk, updates the offset and timestamp, writes
  the header and only then frees the old sectors; chunks of 256 sectors or
  more go to external `c.<x>.<z>.mcc` files.
- `RegionFileStorage`: up to 256 open files.
- `IOWorker`: `pendingWrites`, one entry per chunk, merged by `store`;
  `loadAsync` answers from a pending write before reading the file; "Failed
  to read chunk"; `synchronize(flush)` waits for every pending write; one
  write at a time on a background executor.
- `EntityStorage`: `storeEntities` writes a chunk's entities, an empty chunk
  once as empty (`emptyChunks`); `loadEntities`.
- `ChunkMap`: `saveAllChunks`, `saveChunkIfNeeded` (only `isUnsaved`
  chunks), `scheduleUnload` (a chunk is saved as it unloads), `readChunk`.
- `PersistentEntitySectionManager`: `processChunkUnload` stores and unloads
  a hidden chunk's entities; `autoSave` stores every loaded chunk's entities
  too.

### Differences from Java

1. **Where loaded chunks' state is saved.** Java's autosave writes each
   loaded chunk that changed into its region file, and every loaded chunk's
   entities into `entities/`. Here the level file keeps holding the loaded
   chunks' block entities and entities (as before 1.0) and names them in
   `region_chunks`; their records only get their changed blocks. Unloaded
   chunks are Java's: everything in their records. This keeps each save
   consistent with one level file write instead of a record per loaded chunk.
2. **Entities share the chunk's record** (Java's `entities/` folder is
   separate), as batches appended without rewriting the rest of the record.
3. **Unchanged terrain isn't stored**: a chunk the player never changed
   regenerates from the seed, as before; its record (if it has state)
   holds no blocks. Java stores every generated chunk.
4. **The table** has 4096 slots of 8 bytes (a 3D chunk per slot, no
   timestamps) and is written one entry at a time; Java rewrites its whole
   8 KiB header for every chunk.
5. **No compression and no external files.** Records hold the run-length
   encoded blocks uncompressed (Java compresses with zlib by default), and a
   record's length is 32 bits, so nothing needs Java's `.mcc` files.
6. **A checksum** on every record (Java relies on decompression and NBT
   errors), so a torn or overwritten record is detected.
7. **Damage is reported and kept**: Java logs a chunk it can't read and
   regenerates it; the game also tells the player and copies the damaged
   file aside, as Track 1 does for `chunks.bin`.
8. **Redstone and hopper scheduling** (`redstone`, `automation`) stay in
   the level file for the whole dimension; Java saves block ticks with
   each chunk. They hold scheduled ticks on a world-wide clock and are small
   (Track 3: at most 4 scheduled redstone ticks).
9. **Arrows, thrown items, eyes of ender, fireballs and primed TNT** in
   unloaded chunks still wait in memory and are lost on quitting, as
   before; Java saves them.
10. **Mobs the save leaves out** (non-persistent hostiles that despawn) now
    vanish when their chunk unloads rather than when the game quits. Java
    despawns them by distance before that.

With region storage:

- **Memory no longer follows the distance travelled.** Over 4 hours RSS
  rose from 218 MB (after the first walk) to 320 MB, against 308 to
  1,811 MB in run C. Between the base legs at 70 and 190 minutes it grew
  about 30 MB an hour, and between 190 and 240 minutes 3 MB. The counts that
  grew over those two hours are small, bounded structures, not chunk state:
  populated generation columns (1,404 to 4,404 entries), villager births
  (79 to 133), the stored villagers' bed and job claims (55 to 92), live
  items at the base and the loaded modified chunks around it. No modified
  chunk stayed in memory at any sample; stored entities in memory peaked at
  97 (after a reopen, waiting for the next save, then gone), chests at 110
  and spawners at 47, all the loaded area's.
- **Autosave no longer grows.** The main thread's part of an autosave was
  at most 17.9 ms in 4 hours (base legs, which have the most loaded state to
  put in the level file) and 0–7 ms elsewhere, against 2,223 ms in run C and
  1,195 ms after 90 minutes in the legacy run. A blocking save before a
  reopen waited at most 22.6 ms for the I/O thread. At most 1,829 records
  were queued at once (bound 4,096).
- **Reopening no longer grows**: 363 to 474 ms for the Overworld at every
  reopen (run C: up to 1.3 s and rising), since only the loaded chunks'
  state is in the level file (72 KB at the end) and the chunks read their
  records as they stream in.
- **The disk still grows with what was explored**, as Java's does: 541 MB
  after 4 hours (run C: 505 MB), 222 Overworld, 144 Nether and 42 End region
  files.
- Threads: 9 throughout (the 8 of run C and the region I/O thread).
- **Tick time**: base legs 3.5 ms mean, walks 1.9, Nether 5.1–5.5, End 0.9.

## 6. Remaining gaps and open decisions

1. **Open decision: the loaded chunks' state stays in the level file.** Java
   writes each loaded chunk that changed into its region file at every
   autosave, and every loaded chunk's entities. Here the level file holds
   them (as before 1.0) and names those chunks; records hold everything only
   for unloaded chunks. It is consistent and bounded (the level file is the
   loaded area's: 72 KB in the soak), and moving the rest into records would
   need dirty tracking for every block entity system. The owner may want the
   Java layout instead.
2. **Open decision: redstone and hopper scheduling** stay whole in the
   level file (difference 8). They are small, but their unloaded chunks'
   entries are still session-wide.
3. **Arrows, thrown items, eyes, fireballs and primed TNT** in unloaded
   chunks still wait in memory and are lost on quitting (difference 9).
4. **The save fixture tools and UX-04a's live cycle** read `chunks.bin` and
   the old "saved N modified overworld chunks" log line
   (`tools/save_fixtures/collect.py`, `make-fixture.sh`, `trim_chunks.py`,
   `live_run_of_this_build_starts_saves_quits_and_reopens`). They need to
   read region files before `cycle-current.sh` runs again and before 1.0's
   own fixture is made ([saves.md](../saves.md#what-may-never-change-after-10)
   says every release from 1.0 adds one). Not run for this branch.
5. **Open decision: a uid inside existing keys.** Villagers, golems and
   trader llamas now write `"uid"` into their `villagers` entries; older
   builds ignore it. The policy says new data goes in new keys; this adds a
   field inside an existing key's JSON, as earlier tracks did.
6. **The soak's hot spot** (§4) is worse in this run and not investigated.
7. **Disk use** grows with exploration (541 MB after 4 hours of fast
   travel), as Java's does; nothing prunes it.
8. **Damaged region records** are dropped from their file's table when read
   (the file is copied aside first), so a record from a newer payload
   version regenerates rather than waiting for a newer build. Region files
   of a newer file version were left alone entirely; since the review fixes
   below they are moved aside (S4).
9. **No flush to disk**: like the level file and Java, records aren't
   synced before the table points at them; a power cut can lose a record,
   which then reads as damaged and regenerates.
10. **Not measured**: the frame-time gate (the main thread does less on
    autosave, but nothing was run on the M5); macOS and Windows (CI);
    nobody has played a session with it.
