## What was built

### A headless tick and streaming benchmark

`voxelcraft --bench-tick SCENE` (`src/tick_bench.rs`) runs the main thread's
streaming and simulation work without a window or GPU, so it can be measured
and profiled on Boat. Each frame streams the world around a camera with the
real generation and mesh workers and builds the entity mesh. Every 50 ms of
wall time it runs one game tick in `Game::tick`'s order: world rules, the
automation entity pass, piston pushes and the mob update with natural
spawning. The report covers frame work, frames over 8.33 and 50 ms, each
tick phase, each world-rule step (`simulation::tick_world_rules_marked`)
and where the slowest 1% of frames went. Its six scenes are
`streaming` and `survival` (the live scenes' routes), `entities` and
`automation` (the live scenes' fixtures), `hoppers` (100 chest–hopper
chains and ten hopper minecarts) and `village` (the nearest plains village,
with natural spawning). [Development](../development.md#headless-tick-and-streaming-benchmark)
explains how to run it and profile it with `perf`.

It leaves out the player's own movement and vitals, audio, particles, LAN
and agents, and the reactions the desktop applies to entity events
(sounds, crop trampling, sheep eating grass). It doesn't render. It doesn't
replace the live scenes in `tools/benchmark_scenes.py`, which stay the gate.

### Sign text cached (task item 2)

`render::signs::text` laid out every visible sign's glyphs every frame.
`signs::TextCache` (held by the desktop game's `Mobs`) now lays out each
side once, in the sign cell's own coordinates, and keeps it until the text,
colour, glow, the sign's block state (mount, rotation, wood) or the font
changes. A frame copies the cached vertices, moves them to the camera and
fills in the world light for unlit text. Glowing text's outline is stored as
separate ranges, still drawn only within 16 blocks or for black text, so
that distance needs no rebuild. Sides that leave view drop out of the cache
after eight calls (split screen draws one call per view).

The font is a key: `text(cache, font, …)` takes a font version and clears
the cache when it changes. Callers pass `signs::FONT_VERSION` (0, the
built-in font). Track 1's font seam is to bump that constant when glyph
shapes or advances change, or to pass a run-time value if fonts become an
option.

Measured with `sign_text_frame_cost` (an ignored test: 100 signs, four
15-character lines on both sides, every other sign glowing, 1.09 million
vertices): **36.9 ms** a frame laid out every frame, **3.0 ms** cached. The
cached cost is copying the vertices, nearly all of it the glow outlines' 9×
geometry.

### Streaming (task item 3)

A profile of the streaming route (`perf`, main-thread samples over the whole
run, loading included) put 42% of them in `World::mesh_input`. That function built each mesh job's
34³ light snapshot cell by cell, and light changes remesh up to 27 chunks
each, so it ran often. Changes:

- **Mesh light snapshots on the workers.** The chunk light arrays
  (`lighting::BlockLight`) and column heights are now shared copy-on-write
  (`Arc`, `Arc::make_mut` on write). Queueing a mesh job only takes
  references (`world::LightSources`). The worker builds the snapshot
  (`MeshInput::resolve_light`), a row segment per neighbour, not with
  per-cell lookups. A write after queueing copies the array first, so the
  job still sees the light of the moment it was queued. The synchronous
  remesh path (`mesh_input`) resolves on the calling thread as before.
- **Light invalidation lists changed chunks.** `invalidate_light_meshes`
  scanned every loaded chunk (about 4,000) on every light pass. It now walks
  a list kept as the chunks' flags are set.
- **A streaming light budget.** Instrumenting `update_players` showed
  that its remaining long calls (up to 32 ms) were the unbudgeted light flush
  after about 20 generated chunks arrive at once, or after crossing a chunk
  boundary. `World::set_stream_light_budget` lets each call resolve light
  within a budget; the desktop game uses 2 ms a frame. The rest resumes on
  the next call. No mesh job is queued until light settles, so no mesh
  shows half-spread light, and `pending_jobs` counts that hold, so screenshot
  and benchmark readiness still wait for every mesh. The game resolves all
  light before a frame's first tick, so ticks read exactly the light they
  read when every frame resolved it in full. The default is no budget, so
  the LAN harness, tests and tools are unchanged.

### Tick (task item 1)

Profiles of all six scenes found the tick spread across entity updates
(mob physics and pathfinding), random ticks, natural spawning, fluids, light
and the entity contact pass. The hopper block-entity pass, piston pushes and
game events, which v0.17 added, were small: the whole automation phase was
0.46 ms a tick with 200 hoppers and ten hopper carts, and pistons and block
events were under 0.01 ms. Changes:

- **Random ticks** read the picked block from the chunk directly, not with
  a map lookup per pick. Only picks with a random rule run it, as before,
  and every pick still rolls, so the random sequence is unchanged.
- **`Block::base`** is a table over every state, built once from the
  family checks, which were a chain of about 50 range tests that most blocks
  fell all the way through. A test compares the table with the checks for
  all 32,768 states.
- **The entity contact pass** (pressure plates, tripwire, detector rails,
  wooden buttons, redstone ore) skips any cell no entity can press with one
  table lookup.
- **Trial chambers** reject points outside a chamber's overall bounds
  before testing each piece; spawning asks for every attempt below y = 64.

### Frame loop (task item 4)

The renderer reuses its chunk instance buffer between frames instead of
allocating it every frame. No per-frame loop over the whole world was
found in the frame path. The culling loop visits every chunk mesh, the
sign, shelf, beacon and conduit passes visit those block entities, and the
entity mesh visits loaded entities.

## Behaviour

Identical by construction, and checked by tests:

| Change | Why behaviour holds | Test |
|---|---|---|
| Row-wise light snapshot | The same cells read from the same arrays | `mesh_light_snapshots_match_the_cell_by_cell_reference` (the old loop kept as the reference, over a 4 × 3 patch with missing neighbours, roofs and torches on borders) |
| Snapshots on the workers | Copy-on-write keeps the queued values | `queued_mesh_jobs_keep_the_light_of_the_moment_they_were_queued` |
| Streaming light budget | Light is a fixed point of the queues, and ticks see it settled | `a_streaming_light_budget_settles_to_the_same_light` (the same terrain streamed with no budget and the smallest one, settled light compared) |
| Random ticks | The same picks, the same rolls, the same rules | the existing `world::` growth, copper and fluid tests (990 pass) |
| `Block::base` table | Built from the same function | `the_base_table_matches_the_family_checks_for_every_state` |
| Contact table | Built from the same tests the pass made per cell | the existing `world::redstone`, `gadgets` and `rails` tests |
| Sign text cache | The same layout, moved and lit per frame | `cached_text_is_laid_out_once_and_redrawn_unchanged`, `cached_text_follows_the_camera_without_a_rebuild`, `edits_dyes_glow_state_and_font_rebuild_the_text`, `unlit_text_takes_the_current_light_without_a_rebuild`, `signs_out_of_sight_leave_the_cache` |

Cached sign text differs from the old per-frame layout only in float
rounding: positions are laid out relative to the sign cell and moved by a
32-bit offset, not computed in 64-bit relative to the camera (under 10⁻⁴
blocks). With a streaming light budget, a freshly generated chunk can appear
a few frames later than before while its light settles, and in those frames
mobs and signs in it are lit from light that is still spreading. Gameplay
light is unaffected.

## Gaps and findings left

- **The gate is unmeasured.** These are Boat CPU times. The owner's
  offscreen and windowed suites on the reference M5 decide PERF-02 and
  PERF-03.
- **Tick spikes that changing would alter behaviour.** In the slowest 1%
  of streaming ticks, random ticks take about 7.6 ms and fluids 6 ms:
  - `World::growth_light` (crops, saplings, grass) resolves the whole light
    queue with no budget before reading light, so the first growth check
    after chunks arrive pays for all of their light. Bounding it would let
    growth read light that is still spreading, as Java's threaded light
    engine can. That needs an owner decision.
  - Fluid ticks come in bursts as generated chunks wake their water. They
    are capped per tick, but their order follows hash-set iteration, so any
    change risks a different flow order.
- **Crossing a chunk boundary** (`World::recenter`, unloading the far
  row) still costs about 7 ms on Boat in one frame. Its light now goes
  through the budget, but the unload itself does not.
- **Natural spawning** recomputes `world_surface_height` for every Java
  chunk in range each tick (`SpawnState::new`) and per attempt. It's 2–2.5%
  of the main thread. It's unchanged because a cheaper exact test wasn't
  found.
- **Entity rendering (Track 6's).** `render/entity.rs` and
  `entity::model` were not changed. The mesh build above is the
  CPU-side number.
- **LAN replica.** `World::receive_chunk` on a LAN client rebuilds the
  column heights by scanning every loaded chunk for each received chunk
  (O(loaded chunks) per chunk). It was not measured or changed, since the
  LAN path only gets maintenance.
