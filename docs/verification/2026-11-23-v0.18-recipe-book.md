# v0.18 Track 5: recipe book and discovery (2026-11-23)

Scope: the recipe half of [UX-03c](../requirements.md) and the
`limited_crafting` rule, from the
[v0.18 plan](../roadmap.md#v018-plan-2026-11-23) (item 3). The creative
half of UX-03c is Track 4's. This record says what was built, the Java
sources, how it was checked and what is still unverified. Nothing here has
been seen on screen or played: the owner's play is the hands-on evidence.

## What was built

* **Java's data, embedded.** `tools/extract_java_recipe_book_fixtures.py`
  writes [`recipe_book.json`](../../tests/fixtures/java/26.3/recipe_book.json)
  from the pinned jars; `build.rs` turns it and `recipes.json`'s shapes into
  a static table for [`crafting::book`](../../src/crafting/book.rs). Every
  learnable recipe (1,739) keeps its Java ID, book category, group and
  `show_notification`; Java item names resolve to VoxelCraft items once. A
  recipe the game can't make yet (an unregistered result, or an ingredient
  with no registered alternative) is still learnable and saved, but not
  shown.
* **Unlocking** ([`book/state.rs`](../../src/crafting/book/state.rs),
  [`session/recipes.rs`](../../src/session/recipes.rs)). Each recipe's
  advancement criteria are checked directly (advancements stay DEF-01):
  an item or tag entering the inventory (`inventory_changed`, for each slot
  that changed since the last tick, every filled slot on a player's first
  tick), ten occupied inventory slots (the chest), `tick` (the crafting
  table), the player's box inside water (`enter_block`, boats and rafts),
  and crafting or smelting the recipe (`RecipeCraftingHolder.awardUsedRecipes`,
  the furnace's `RecipesUsed` tally). A new unlock is highlighted until a
  page shows it, and recipes with `show_notification` queue the
  "New Recipe(s) Unlocked!" toast (the crafting table's doesn't notify).
  All recipe advancements have one requirement group, so any criterion
  unlocks; `has_the_recipe` needs no check.
* **The book** ([`app/recipe_book.rs`](../../src/app/recipe_book.rs)):
  Java's 147 x 166 book left of the menu (`OFFSET_X_POSITION` 86), or over
  it below 379 GUI pixels wide, where picking a recipe or Escape closes it;
  the menu moves right as `updateScreenPosition` moves it. Tabs per book
  type with Java's icons (compass search tab, then the categories; a
  category tab shows only when something fits), the 81 x 14 search box
  (`Search...` hint, 50 characters, T focuses it), the filter button with
  "Showing Craftable" / "Smeltable" / "Blastable" / "Smokable" and
  "Showing All", 20 buttons a page in 5 x 4, page arrows with "Next Page" /
  "Previous Page" and the `x/y` count. Buttons are red without the items,
  shadowed when they group several recipes ("Right Click for More"; right
  click lists them), and pulse once when they show new recipes. The ghost
  recipe fills the grid (or furnace input, empty fuel slot and output) with
  red-backed, faded items cycling every 30 ticks. Enter or Space places the
  last recipe again. The green book button sits where Java puts it relative
  to the grid: under the 2x2 grid, left of the 3x3 grid, left of the
  furnace input.
* **Placement** ([`book/place.rs`](../../src/crafting/book/place.rs),
  [`book/stacked.rs`](../../src/crafting/book/stacked.rs)):
  `ServerPlaceRecipe` and `PlaceRecipeHelper` on the shared grid and
  furnace. The grid must fit back into the inventory first unless the
  player is in Creative (who spills what doesn't fit); with the items for
  one set the grid empties and refills (one set; one more each click while
  the grid shows that recipe; every set with shift), clamped to the used
  items' stack sizes; without them the grid empties and the ghost shows.
  Only undamaged, unenchanted, unnamed stacks of the 36 main slots are
  used. Small patterns centre as Java's helper centres them. Furnace books
  fill the input, return the input and output and leave the fuel. Nothing
  is created: the grid's own `Grid::result` makes the result.
* **Per-player storage.** The host saves the `recipe_book` property in
  `level.txt`; every agent, controller and LAN profile saves a
  `recipe_book` field. Both hold Java's `recipeBook` data as JSON:
  `isGuiOpen`, `isFilteringCraftable`, `isFurnaceGuiOpen`,
  `isFurnaceFilteringCraftable`, `isBlastingFurnaceGuiOpen`,
  `isBlastingFurnaceFilteringCraftable`, `isSmokerGuiOpen`,
  `isSmokerFilteringCraftable`, then `recipes` and `toBeDisplayed` as
  `minecraft:` recipe IDs. Missing settings read false (Java's defaults),
  unknown IDs are dropped (`loadUntrusted`), unreadable text gives the
  initial book.
* **Legacy players.** A save without recipe data starts from Java's initial
  state (nothing known). Its first tick reports every filled inventory,
  armor and off-hand slot, as Java's slot listener does on joining, so the
  saved inventory unlocks what it proves; the crafting table unlocks on
  that tick. No other saved state matches a recipe criterion (statistics
  and advancement progress don't exist), so nothing else is granted.
* **`limited_crafting`** (`doLimitedCrafting`) is stored and enforced:
  with it on, a crafting grid shows and gives a result only for a known
  recipe; special recipes (fireworks, banner copies, map extending and the
  rest) always craft (`RecipeCraftingHolder.setRecipeUsed`). It applies to
  the 2x2 and 3x3 grids of every player and the agent's `craft` and
  `recipe`; the crafter block is unaffected, as in Java. Furnaces ignore
  it, as in Java.
* **Every input path.** Mouse and keyboard as above. Controllers: the
  crafting tab (LB/RB) is the recipe book, titled with its filter; A
  places one set through the book and takes it, Y every set, X toggles the
  craftable filter, missing-ingredient recipes are tinted red and shown
  recipes lose their highlight. CLI agents: `recipe <id> [max]`,
  `recipes [all|craftable] [query]` and `observe`'s `recipe_book`
  (see [agents](../agents.md)). LAN guests: the host sends the guest's book
  in its snapshot when it changes, with the rule; the guest's clicks,
  seen recipes and settings go to the host as `recipe_place`,
  `recipe_seen` and `recipe_settings` commands, and the host places with
  the same transaction on the guest's grid or furnace.

The extractor reads class files only for static constants
(`IMAGE_WIDTH`, `ITEMS_PER_PAGE`, `DISPLAY_TIME` and the like) and the
order of static field and string references in static initializers (tab
icons and categories, settings keys, the category registry). It fails on
any criterion, requirement shape, predicate or recipe type it doesn't know.

## Checks run

All on Boat through `scripts/boat-check.sh`; `cargo fmt --check`, Ruff and
the doc-link check ran here.

```sh
uvx ruff@0.17.5 check tools/extract_java_recipe_book_fixtures.py
uvx ruff@0.17.5 format --check tools/extract_java_recipe_book_fixtures.py
python3 tools/extract_java_recipe_book_fixtures.py server.jar client.jar --output ...  # reproduces the fixture byte for byte
cargo fmt --check
scripts/boat-check.sh -- 'cargo clippy --profile ci --locked --lib --bins --tests -- -D warnings && ...'
```

The results are in the hand-off report; CI runs the full suite.

Tests (`tests/recipe_book.rs`, `crafting::book` unit tests, the app's
`recipe_book` unit tests, `rules` tests):

* Java's tabs, icons, search tabs, category order, filter and toast labels,
  settings keys and layout constants against the fixture.
* Every learnable recipe's ID, category, group and notification against
  the fixture; specials are not learnable; every VoxelCraft crafting result
  has a book recipe.
* Every shown recipe, at its first alternatives, crafts its result through
  `Grid::result` (or cooks in its furnace kind) and matches its own
  placement.
* Item criteria: for every item a criterion names, holding it unlocks
  exactly the recipes that name it (or a tag holding it), plus the
  crafting table's `tick`; ten slots and water; slot changes after the
  first tick; crafting and smelting teach; toasts only for notifying
  recipes.
* Pages: 3x3 recipes hidden in the 2x2 grid, tabs, search, craftable marks
  and the filter, furnace books by cooking type, grouped buttons.
* Placement: one set, one more, shift for all; several stacks; one-stacking
  items; ghost on missing items; damaged or named items unused; a grid that
  can't go back stays (Creative spills); furnace input, output and fuel.
* `limited_crafting`: known recipes and specials only; a migrated player
  with logs reaches a wooden pickaxe through planks, sticks and the table.
* Saves: round trip, Java's keys, unknown IDs, missing settings, junk,
  legacy players checked against their saved inventory.
* The agent: `craft` under the rule, `recipe ... max`, `recipes`, `observe`.

## Differences from Java

* Item choice: when several item types fit an ingredient, placement takes
  them in inventory order (hotbar first); Java's `RecipePicker` takes them
  in hash order. Whether a recipe fits, and how many sets, is the same.
* Order: buttons follow Java's recipe ID order, grouped as
  `ClientRecipeBook` groups; Java's client keeps known recipes in a hash
  map keyed by display ID, which is close to that order for large books.
* Map cloning shows one entry (one map); Java shows eight displays.
* The grouped-recipe overlay lists the results; Java's draws each recipe's
  grid in miniature.
* The book, buttons, tabs, ghost and toast are drawn with original shapes
  and colours, not Java's textures; the toast slides over 600 ms.
* Unlock timing: changed slots are checked once a tick, after every change
  in that tick; Java checks each slot change as it happens.
* Water: the player's box overlapping a water cell (not a waterlogged block
  or bubble column) counts as entering it.
* Controllers have no ghost or toast (the crafting tab lists recipes
  instead of filling a grid), and A/Y place and take at once, as the
  controller crafting tab did before.
* A LAN guest shows the ghost when its own copy says the items are missing;
  Java's client waits for the server's reply.
* The host console has no `recipe` command (agents do).
