# v0.18 Track 1: typography, contrast and accessible text — 2026-11-23

Status: **Implemented, unverified.** No owner play. Branched from
`v018-polish-performance` at `39fe5bc` as `v018-t1-typography`. Rows: the
text and contrast parts of UX-03f (scope items 1 and the text part of 8).
Seen only in software-rendered captures on Boat, which show appearance,
never performance.

## What was built

1. **An original pixel font**
   ([`assets/font/glyphs.txt`](../../assets/font/glyphs.txt), parsed by
   [`src/font.rs`](../../src/font.rs)). Drawn for this project as text
   bitmaps: the 94 printable ASCII glyphs and 66 Latin-1 and Latin
   Extended-A glyphs (symbols, Æ, Ð, ß, Ł, Œ, ŉ and the like) by hand, and
   157 accented letters composed from 14 shared marks (acute, caron,
   ogonek and so on) placed by rule over or under the base letter's ink.
   With the two spaces that makes 319 characters, plus a dotless j helper
   and a missing-glyph box. Metrics are Java's: 9-pixel lines, capitals on rows
   0–6, x-height 5, one-pixel descenders on row 7, accents over capitals
   up to 3 rows above the line (Java's accented glyphs are 12 rows with
   ascent 10), marks below on rows 7–8, and a shadow 1 pixel down and
   right at 25 % brightness. **Every advance equals Java 26.3's** (317
   characters checked against the fixture; the other two are below), so
   Java's layouts, button labels and the signs' 90-pixel rule fit the same
   text. The atlas is 256 × 252 R8 (16 × 12 cells). The `font8x8`
   dependency is gone.
2. **One measurement everywhere.** `font::width` is Java's `Font.width`
   (the advances, trailing gap included) and `font::ink_width` /
   `Ui::text_width` the ink for centring. UI labels, tooltips, the HUD,
   held-item names, subtitles, books (`books::wrap`), sign text
   (`render/signs.rs`), entity name tags (`entity/model/labels.rs`, which
   used a fixed 8-pixel cell before), the command console (it wrapped by
   counting characters) and every text field draw and measure through the
   font. `font::VERSION` (2; 1 was `font8x8`) changes with any glyph, for
   Track 10's cache of sign text geometry.
3. **Accented user text.** `font::allowed` is Java's
   `StringUtil.isAllowedChatCharacter` (no controls, no `§`) limited to
   what the font draws. Signs, book pages and titles, world names, edit
   boxes and the creative and recipe-book searches take it. Text fields
   keep the caret and selection on character boundaries: Left, Right,
   Backspace, Delete, clicks, selection, cut/copy/paste and the scrolled
   view all step whole characters, and length limits count characters
   (Java's UTF-16 length, the same for every character the font draws).
4. **Signs.** Saved sign text was already UTF-8 bytes in hex, so the
   format is unchanged and old saves load as written. New edits follow
   Java's rule: an insertion is refused whole if the line's `Font.width`
   would pass 90 (60 hanging) pixels, as `SignEditScreen`'s
   `TextFieldHelper` does; the editor no longer cuts a line it was opened
   with. The renderer shows the first line Java's `StringSplitter` wraps a
   long line to (the last space that fits, else by character), or, if
   longer, everything the old font's 90-pixel rule showed, so **no sign
   written before v0.18 loses a character** (`font::legacy_prefix`, with
   `font8x8`'s ASCII widths kept as a 95-entry table; old lines were
   ASCII only). The controller sign editor follows the same rules.
5. **Colour pipeline.** Every UI colour is written as sRGB and converted
   once: `Ui::quad` runs it through `render::ui::linear` (the exact sRGB
   curve, alpha untouched), for flat colours and texture tints alike.
   `render::ui::rgb(0xC6C6C6)` writes a constant as its hex. The two places
   that already decoded a dye colour with `powf(2.2)` (`patterns.rs`,
   `components::dye_tint_f32`) now pass sRGB values. `render::ui::shade`
   gives a black overlay at Java's alpha (Java blends sRGB values, the
   game blends linear light).
6. **States and contrast.** Menu button colours are sRGB hexes chosen for
   the guide's rules: white on `#6B6B6B` (5.3:1), `#FFFFA0` on the hovered
   `#646E9C` (4.8:1), `#A0A0A0` on the disabled `#4A4A4A` (3.4:1, 1.6 times
   less than enabled). Hover now draws the white 1-pixel frame focus had,
   and a disabled button stays flat, so no state is told by colour alone.
   Scrolling lists get Java's list backing (`menu_list_background`, black
   at 112/255) across the screen's width.
7. **Label fit.** With Java's widths, labels that the old, wider glyphs
   clipped now fit (Max Framerate, Render Distance, the inventory's
   search hint). Labels scroll only when `Font.width` passes the room
   inside Java's 2-pixel `TEXT_MARGIN` (it was 4). Overflow handling stays
   for long content.
8. **Comparison scenes** in `tools/capture_scenes.json`: `sign-text`
   (three oak signs with accented, ASCII and full-width lines) and
   `accessibility-settings` (the text options).

## Tests

  the accented glyphs' ascent and the signs' widths and heights against
  Java; accented sign text through `set_sign_text`, a level save and load
  and the LAN copy (`wood_near` → `replace_wood`); a pre-v0.18 sign save
  entry (built by hand in the old format) loading unchanged and saving
  again; accented book pages, title and author through
  `stack_to_string`/`stack_from_str`, and book wrapping by the shared
  measurement.
- `font::tests`: coverage of the three ranges, metrics (rows of capitals,
  x-height letters, descenders and accents), run decomposition, the
  allowed set, prefixes and Java's first-line wrap, the old font's line
  rule, and parse errors.
- `render::ui` tests: every sRGB byte survives `srgb_to_linear` and the
  GPU's encoding unchanged; `Ui::quad` converts flat colours and tints;
  `shade` darkens as Java's alpha; text quads sit where the font says and
  clipping keeps them inside the clip.
- `render::signs` tests: lines cut between accented characters, Java's
  wrap at a space, and every old-font ASCII line shown whole.
- `app::gui` tests: accented typing, Left/Backspace/Delete over two-byte
  characters, selection, cut and paste, clicks by the shared measurement,
  the field drawn wider than its box, and the sign's width rule (refusing
  overflow whole, keeping a wider opened line). The existing clipboard
  test now expects `é` kept and an unsupported character dropped.
- Option persistence: Track 9's `textBackgroundOpacity` and
  `backgroundForChatOnly` tests already cover the text options; this track
  adds no option.

## Differences from Java

- **The glyphs are VoxelCraft's own**, with Java's advances. Shapes differ
  wherever they were drawn differently.
- **Coverage stops at Latin Extended-A.** Java falls back to Unifont for
  every other character; here they draw as a box and can't be typed,
  pasted or saved onto signs (a sign or book drops them, as an en dash in
  the test shows). Two characters in range come from Java's Unifont,
  which isn't in the jar: the no-break space is drawn as a space (advance
  4) and the cedilla `¸` with advance 3. Java's advances for them are
  unchecked.
- **Force Unicode Font is not added:** it switches Java to its Unifont
  font (`minecraft:uniform`), and there is no second font here, so it
  would be inert. Japanese Glyph Variants doesn't apply either.
- **Blending** happens in linear light on the sRGB surface where Java
  mixes sRGB values. Opaque colours now show exactly as written; a
  translucent colour other than black still looks a little different
  from Java's at the same alpha. `shade` makes black overlays match.
- **The old font's line rule** is kept for display of pre-v0.18 sign
  text: Java has no such rule.
- **World list details** keep Java's `#808080`, which over the list
  backing measures 2.7:1 (2.5:1 before this track) against the sky behind it (Java's own screen
  is similar, with a blurred panorama). The guide asks 4.5:1 for ordinary
  text; Tracks 2 and 7 own the list's look and the menu blur.
- Name tags keep an opaque dark backing: Java's follows Text Background
  Opacity (`getBackgroundOpacity(0.25)`), which needs translucent entity
  geometry the entity pass doesn't have.

## Measurements

Headless on Boat (`large`, x86_64), `cargo test --profile ci --bin
voxelcraft text_cost -- --ignored --nocapture`, 40 shadowed lines of 57
characters (2280 characters, 3920 quads) built into one reused vertex
buffer, and 3920 flat rectangles:

| Build | Text, per frame | Rectangles, per frame |
|---|---|---|
| Base `39fe5bc` (same test added) | 38–42 µs (17 ns a character) | 32 µs |
| First version of this track | 92–101 µs | 88–100 µs |
| This track (`Ui::quad` always inlined) | 47 µs (21 ns a character) | 35 µs |

The first version was 2.5 times slower: the conversion check made
`Ui::quad` too big for the inliner, so every UI quad became a call (a
copy of the same code inlined into the test ran at base speed, in the
`ci` and `--release` profiles alike). `#[inline(always)]` on `quad` and
`ndc` brought it back; what remains is the colour check (one comparison
per quad; a conversion costs about 9 ns and happens once per colour
change) and the font table lookups, about 2 ns a quad. Sign text and name
tags are built from runs of ink per glyph row as before; name tags used a
quad per pixel and now use a quad per run. The frame-time gate wasn't
run (it needs the reference Mac).

## Gaps

- Nobody has seen the font on a real GPU or in play; captures only.
- Glyph shapes are a first drawing. Some rarely used Latin Extended-A
  forms (ĸ, ŉ, Ŋ, ð, ¤, the vulgar fractions) are the least tested by eye.
- The slot fill constant shows 115 where Java's is 139 (Track 2's
  palette). The world list's detail text contrast (above) and the in-world menu
  dimming (`0.78` linear, lighter than Java's `#C0101010`–`#D0101010`
  gradient) are left to Tracks 2 and 7.
- Name-tag backing opacity (above).
- Folder names for worlds still drop non-ASCII characters (`folder_for`);
  the world's display name keeps them.
