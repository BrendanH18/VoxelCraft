## Result

**Not yet a valid reference baseline, and the 240 FPS gate fails.**

Twelve of the fifteen runs are valid. All three entity runs failed a harness
check that turned out to be a fixture bug (below). Every valid run completed
exactly 20 ticks per second, with no pause time and no unpresented frames.

The 120 Hz question from the first attempt is mostly settled. Presentation
is not capped: runs average 470–634 FPS at a median frame time of about
1.55 ms. Survival run 3, however, had 2,031 of 28,039 frames (7%) paced at
exactly 8.33 ms, so the display sometimes paces at 120 Hz.

## Findings

- **Streaming stalls are the largest problem.** Each 180 s streaming run has
  about 452 frames over 50 ms (worst about 125 ms), pulling the 1% low down to
  17 FPS. There are none for the first 44 s. After that they come in bursts of
  about eight consecutive 50–75 ms frames every 2.2–2.5 s. At the route's
  12 blocks/s, that is one burst per 27–30 blocks, close to the 32-block
  storage-chunk size. It points to per-chunk-row work on the main thread
  (chunk insertion, lighting, mesh uploads or generation-herd population)
  once the camera leaves the preloaded area. Profile this first.
- **The slow tail elsewhere is modest.** Automation passes every run.
  Survival and building miss the 1% low gate mostly through occasional 8.33 ms
  frames and short spikes, not through slow typical frames.
- **Harness defect 1: the entity population.** Since the 2026-10-15
  spawn-category work, chunk generation adds creature herds as columns finish
  loading and lighting settles. Java's `spawnMobsForChunkGeneration` runs
  regardless of `doMobSpawning`. The scene counted its expected population
  (320) while herds were still arriving, so all three runs reported drift,
  although the count stayed at 347 from sample start to end. **Fixed**
  (uncommitted): `src/app/benchmark.rs` now records the 160 fixture mobs and
  removes every other mob until sampling starts, and the check expects 160. A
  quick smoke run held 160/160.
- **Harness defect 2: the simulation distance.** `benchmarks/scenes.json`
  specified 128 blocks, a value from before Java simulation distance existed,
  but the game ran at its default of 10 Java chunks (160 blocks) and nothing
  checked it. **Fixed** (uncommitted): the specification now says 160, and the
  runner rejects any run whose view or simulation distance differs from the
  specification (`tools/test_benchmark_scenes.py` covers it).

## Next steps

1. **Commit and re-run.** Commit the harness fixes and run the full suite
   again. The entity runs need the fixed fixture, and the runtime fingerprint
   changes with `benchmark.rs`, so the other scenes must be re-measured too.
2. **Record the baseline.** If every run is valid, that run is the M0
   reference baseline (PERF-01) whether or not it passes 240 FPS.
3. **Profile streaming.** Profile the streaming stalls and treat them as the
   first performance work (§6, v0.20 gate; earlier if they affect play).
4. **Watch the 8.33 ms episodes.** If they recur, test with the window on an
   external display to see whether the built-in panel causes them.
