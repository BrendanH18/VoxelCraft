## What changed

### Generation 7: the End's decoration (GEN-04b)

`world::end::decoration` (new) ports `applyBiomeDecoration` for the End
biomes; it runs only in generation 7 (`EndGen` with Java's noise), so
generations 1–6 don't move. Each feature draws from a `WorldgenRandom`
(Xoroshiro) seeded `setDecorationSeed(world seed, chunk x, z)` then
`setFeatureSeed(decoration, index, step)`, with Java's indices (the jar's
`FeatureSorter` over `TheEndBiomeSource`'s biomes):

| Step | Feature | Index | Placement |
| --- | --- | --- | --- |
| 0 `RAW_GENERATION` | `end_island_decorated` (`small_end_islands`) | 0 | `rarity_filter` 14, `count` 1 (weight 3) or 2 (weight 1), `in_square`, `height_range` uniform 55..=70, `biome` |
| 4 `SURFACE_STRUCTURES` | `end_gateway_return` (`end_highlands`) | 0 (`end_spike` is 1) | `rarity_filter` 700, `in_square`, `heightmap` `MOTION_BLOCKING`, `offset` y uniform 3..=9, `biome` |
| 9 `VEGETAL_DECORATION` | `chorus_plant` (`end_highlands`) | 0 | `count` uniform 0..=4, `in_square`, `heightmap` `MOTION_BLOCKING`, `biome` |

`FeaturePlacer` runs the modifiers depth first, so each copy a `count`
makes is spread, filtered and placed (drawing the feature's own numbers)
before the next. The `biome` filter reads through `BiomeManager`'s zoom
(`biome_zoom`) at the placed block. `MOTION_BLOCKING` is 26.3's tag
(`#blocks_motion_in_heightmap`, the list `precipitation::motion_blocking`
already loads): chorus and the gateway block aren't in it, end stone,
bedrock and purpur are; it counts the terrain, the islands, the chunk's
End city pieces (placed in step 4 before its features) and, for chorus,
the return gateway.

- **Small islands**: `EndIslandFeature` (the existing `java_island`, now
  `island_with` any `nextInt`) on the decoration random, painted in every
  section they reach.
- **Return gateways**: `EndGatewayFeature` (the existing `gateway_block`),
  exit (100, 50, 0), exact. Using one takes the player to that spot's
  bottom centre (`getPortalPosition` with `exactTeleport`): nothing is
  built or searched, the motion is kept and the portal cooldown starts
  (`Arrival::Gateway` gained `exact`). A generated one is a new block
  entity of age 0 (`World::generated_gateways`, taken into the fight's
  gateways each tick), so it shows the spawn beam when first loaded, as
  Java's does; it cools down when used like any gateway. A thrown pearl
  takes the player through it as through any gateway.
- **Chorus**: `ChorusPlantFeature` (air at the heightmap, end stone below)
  and the existing `generate_plant`, on the decoration random. Java
  decorates chunks in whatever order the server reaches them, and a plant
  that meets one already grown stops (and every later draw of its chunk
  moves). VoxelCraft fixes the order west to east, then north to south: a
  chunk's plants see the plants of the neighbours before it, each as that
  neighbour grows them alone.

### The arrival platform (item 3: no generation change)

Java 26.3 does build the platform with the terrain: `the_end`'s biome
lists `end_platform` in step 10 (`TOP_LAYER_MODIFICATION`), a
`fixed_placement` at (100, 49, 0) running `EndPlatformFeature` with
`dropResources` false. `EndPortalBlock.getPortalDestination` builds it
again on every arrival with `dropResources` true. Track 4's note ("Java
builds it on arrival only") misread this; VoxelCraft's generation already
matched, so it stays. What changed is the arrival: every block of the
5 x 4 x 5 that isn't the obsidian floor or the air above is now destroyed
with its drops (`destroyBlock(pos, true)`, break particles), not silently
replaced, and the player keeps their pitch (`Relative.X_ROT`); the yaw
was already Java's west.

### The dragon (PRO-05)

- **Hits in `DYING`.** Java's `EnderDragonPart` stays pickable and alive
  until the dragon is removed, and `EnderDragon.hurt` refuses everything
  in `DYING`. The fight's and wild dragons' ray tests no longer skip a
  dying dragon, so an arrow strikes it, does nothing, and is deflected
  back at a tenth of its speed (`deflect(REVERSE, .., 0.2)`), in the
  death flight and in the death rise; melee hits land and do nothing.
- **Growls.** A new `MobSound::DragonRoar` plays Java's client growl at
  the dragon (volume 2.5, pitch 0.8–1.1): every tick of
  `SITTING_ATTACKING` (`doClientTick`), and in flight when `--growlTime <
  0` (first on the 101st tick, then every 201–400). Before, the roar
  growled once at its start and the occasional growl came from the head
  while perched too.
- **Flight.** `Dragon::fly` is `aiStep`'s movement in Java's arithmetic:
  the fly speed as a float, the climb clamp, `Mth.wrapDegrees`, the
  `Mth.sin`/`Mth.cos` tables, Java's table-driven `Mth.atan2` (with
  `fastInvSqrt`), the float turn (`yRotA`), `moveRelative` through
  `getInputVector`, the `0.8F` in-wall scale and the `0.91F` drag, each in
  Java's order. With no target (a sitting phase) the dragon now stays put
  and keeps its motion, as Java's does, rather than zeroing it. `inWall`
  is the last tick's `checkWalls` of the head, neck and body (it was the
  body and wings). `tick` follows `aiStep`'s order: `checkCrystals` (now on
  `tickCount`, not the phase's ticks) before the wing beat, the yaw wrapped
  before the flight history records it, the phase, the flight, the parts,
  then the walls. The non-Java ceiling clamp is gone.

## Remaining differences

- **Decoration order.** Where two chunks' chorus meet, Java's result
  depends on which chunk its server decorated first, which a player's
  path decides; VoxelCraft fixes west to east, then north to south, and
  each chunk sees its earlier neighbours' plants as they grow alone (a
  chain of three meeting chunks can differ from any Java order). Islands,
  cities and gateways around a chunk are always treated as already there.
- **Cities.** The fixture grids hold no End city, so decoration beside
  cities is untested against the jar; VoxelCraft's city blocks are
  original (FE-02), so heightmaps over them follow VoxelCraft's pieces.
- **Projectiles.** Only arrows strike the dragon (in any phase), as
  before; snowballs, eggs, pearls, potions, wind charges and fireballs
  still pass through it. A deflected arrow isn't turned 170–190° nor
  dropped as an item once almost still, as Java's is.
- **`inWall` with `mobGriefing` off**: Java counts every block that isn't
  air or `#dragon_transparent` as a wall; VoxelCraft only the blocks the
  dragon can't break (the dragon's tick doesn't see the game rule).
- **Randomness.** The flight from a target is Java's, but the phases'
  random choices (nodes, strafes, growl intervals, crystal scans) use
  VoxelCraft's random, so a run never repeats a Java run's route.
- **Arrival**: Java keeps the player's motion through the End portal
  (`Relative.DELTA`); VoxelCraft still stops them.
