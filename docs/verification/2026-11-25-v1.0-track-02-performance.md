## Background

In play the owner first found v0.18 slower than v0.17 at higher render
distances, then judged it fine; nobody measured it. The v0.18 delivery
record ([§3.8](../delivery-records.md#38-v018-delivery-record--2026-11-25))
lists suspects read from the diff. This track addresses each one:

| Suspect | What changed |
|---|---|
| Entities, beams and conduits built to `Fog::end()` (render distance × √2) | Built to Java 26.3's own distances |
| Fancy clouds at 128 chunks, about 35,000 faces drawn twice | One pass as Java draws them; Java's default Cloud Distance (64); buffer bounded |
| The chunk shader's sRGB lightmap and fog (`pow` on nearly every fragment) | The constant fog colour encoded once per frame; the lightmap once per vertex on uniformly lit quads; output unchanged |
| The 2 ms streaming light budget | Reviewed and kept; see [below](#the-streaming-light-budget) |
| Growth light flushing the whole light queue (owner, 2026-11-25: bound it) | Bounded to the light work that can reach the cell; the read is exact |

## What changed

### Entity, beam and conduit distances

`entity::draw_distance` (new) decides what the entity mesh builds, with
Java 26.3's two tests:

- **Tracking.** `ChunkMap.TrackedEntity.updatePlayer`: the integrated server
  sends an entity to a player while their horizontal distance is at most
  `min(clientTrackingRange × 16, viewDistance × 16)` blocks. The table
  `TRACKING` has `clientTrackingRange` for all 161 entity types in
  `EntityTypes` (the builder's default 5, for example the dolphin's,
  included); every `MobKind` resolves to its Java id. Tracking is measured
  from the view's player, not the camera.
- **Rendering.** `Entity.shouldRenderAtSqrDistance`: the squared camera
  distance is below `(size × 64 × viewScale)²`, `size` being the mean side
  of the bounding box (`AABB.getSize`), with `viewScale =
  clamp(renderDistance / 8, 1, 2.5) × entityDistanceScaling`
  (`LevelExtractor.extractVisibleEntities`). `entityDistanceScaling` is 1.0,
  the Fancy preset's (`GraphicsPreset.apply`); VoxelCraft has no Entity
  Distance option. The overrides VoxelCraft draws follow Java: item frames
  use 16 for the size (`ItemFrame`), armor stands `4 × size × 64` without
  `viewScale` (`ArmorStand`), phantoms always pass (`Phantom`), paintings
  use their box, experience orbs (0.5 × 0.5, tracked within 6) and
  minecarts (0.98 × 0.7, 8; the cushion 1 × 0.25, 10) their types'.
- **Beacon beams** draw while the beacon's centre is within
  `renderDistance × 16` blocks horizontally (`BeaconRenderer.getViewDistance`
  and `shouldRender`); **conduits** within 64 blocks
  (`BlockEntityRenderer.getViewDistance`, which `ConduitRenderer` keeps).

On top of Java's tests nothing the fog hides completely is built (the
environmental fog's end on spherical distance, the render-distance fog's
on cylindrical distance, as `fog.glsl` measures them). Java would draw
those in the fog's colour, so leaving them out changes no pixel; it is
tighter than v0.18's single `Fog::end()` sphere.

At render distance 8 (16 Java chunks, `viewScale` 2) a zombie now draws to
128 blocks horizontally (its tracking range) and 134.4 vertically; a cow to
136.5 blocks (its box), short of its 160-block tracking. v0.18 drew both to
362 blocks (√2 × the 256-block render-distance fog). At render distance 24
`viewScale` is Java's maximum 2.5 and tracking caps most mobs at 128 or 160
blocks, where v0.18 drew to the environmental fog's 1,024.

The desktop game and split-screen views pass each view's player and fog
(`split::Atmosphere::draw_distance`). Tests, examples and tools that pass a
plain distance keep the old sphere (`DrawDistance::fog_only`). The dropped
item, projectile, End crystal and dragon builders are unchanged (few, and
mostly short-lived).

### Clouds

- **One pass, as Java draws them.** Java 26.3 draws clouds without its
  order-independent transparency through `RenderPipelines.CLOUDS`:
  translucent blending, `DepthStencilState.DEFAULT` (a greater-or-equal
  reverse-Z test with depth writes) and back faces culled; `FLAT_CLOUDS`
  culls nothing. v0.18 drew every face twice, a depth-only pass then a
  colour pass with an equal test. `render::clouds` now draws once with
  Java's state. Faces are built nearest ring first (`CloudRenderer.buildMesh`'s
  order), so the nearest surface writes its depth before anything it hides
  and the hidden faces fail the test: the same nearest-surface picture at
  half the vertex work. `faces_come_nearest_first_along_every_ray` checks
  the order the argument rests on.
- **Fast clouds are no longer culled**, as `FLAT_CLOUDS`: v0.18 culled their
  one downward face, so Fast clouds vanished from above the layer.
- **Bounded buffer.** The face buffer is sized by Java's bound for the
  radius (`CloudRenderer.getSizeForCloudDistance`: four faces per cell over
  `2 (r + 1)²` cells, plus 54 inside faces), allocated once per Cloud
  Distance rather than grown by doubling. `build_never_exceeds_javas_bound`
  checks it for the generated pattern, a checkerboard (the most side faces)
  and a full sky.
- **Default Cloud Distance 64.** `Options.cloudRange`'s own default is 128,
  but a fresh Java 26.3 client never shows it: `Minecraft.<init>` calls
  `Options.applyGraphicsPreset`, the preset defaults to Fancy, and
  `GraphicsPreset.apply` sets Cloud Distance to 32 (Fast), 64 (Fancy) or 128
  (Fabulous). `DEFAULT_CLOUD_RANGE` is now 64. The atmosphere extractor
  records the presets' values and the startup call, and checks them.

Faces at the old and new defaults (`cloud_and_fog_cost`, Boat):

| Cloud Distance | Fancy, below the layer | Fancy, inside | Fast | Java's bound |
|---|---|---|---|---|
| 128 (v0.18's default) | 35,027 | 65,831 | 30,804 | 236,726 |
| 64 (Java's default) | 9,172 | 17,339 | 8,167 | 60,606 |

With one pass, Fancy clouds below the layer go from 420,000 vertices a
frame (35,027 faces, 6 vertices, 2 passes) to 55,000 (9,172 faces, 6
vertices, 1 pass). A player who keeps 128 draws 210,000.

### Chunk shader

The output stays the same; only where the work happens moves:

- **Fog colour.** The fog blends in sRGB as Java's does, so v0.18 encoded
  the fog colour, a per-frame constant, with three `pow`s on every fogged
  fragment, which in the Overworld is nearly every fragment (its
  environmental fog spans 0 to 1,024 blocks). The CPU now encodes it once
  per frame (`Globals::fog_srgb`, the same `encode` the target's
  conversion follows), and a fully fogged fragment returns the fog colour
  without converting at all.
- **Lightmap.** The Overworld's Java lightmap (`overworld_light`: the
  `lightmap.fsh` sum, night vision and Brightness, then three `pow`s to
  linear) ran per fragment. When all four corners of a quad carry the same
  light byte, as in open sunlit terrain and dark caves, the vertex shader
  works it out once (`overworld_parts`) and passes it flat; the fragment
  multiplies in the interpolated corner shade in the same order as before.
  Quads with differing corner light still use the per-fragment path.

The remaining per-fragment `pow`s are the fog blend's own encode and
decode of the surface colour (six). No cheaper form gives the same bytes:
a lookup or a low-resolution lightmap texture like Java's `LightTexture`
interpolates differently. Rendering in gamma space as Java does would
remove them, but that is an architecture change, recorded as an open
decision. The entity and block-model shaders keep the v0.18 form.

### Growth light (owner decision, 2026-11-25: bound it)

Growth rules (crops, saplings, grass and mycelium spreading, sniffer and
flora rules through `growth_light`), snow layers melting, frosted ice in the
End and mushrooms surviving used to resolve the whole light queue before
reading light. They now resolve it only when queued work could change the
light at the cell they read (`World::settle_light_at`), and they read
exactly the settled value either way.

Why that is exact: resolving the queues changes only cells within 30
blocks of queued work. A removal clears at most 15 steps out (each step
loses a level below the implied sky sources) and the relight from its
edge reaches at most 15 more. Each light queue keeps the set of storage
columns (32 × 32 blocks) that received work since it was last empty
(`LightUpdates::columns`, added to as entries are queued and cleared when
the queue drains). Work queued only outside the cell's column and its
eight neighbours is at least 33 blocks away, so the light there already
holds its settled value. Work found while resolving stays within reach of
the queued work it came from, so the columns noted when that work was
queued still bound it.

Where the cost actually was. Since v0.18's streaming light budget the
desktop game resolved all light before a frame's first tick, so the growth
check's flush was usually empty and the cost had moved to that pre-tick
flush: up to 23–30 ms in single frames when a burst of chunks arrived
([v0.18 record](2026-11-23-v0.18-performance.md)). Bounding growth alone
would change nothing in the game, so the pre-tick flush is bounded the
same way: `World::settle_light_for_ticks` resolves queued light only if
some of it lies within a storage column of the block-ticking area around
any player (Java's level-32 chunks: random ticks, precipitation, block
entities, and the entity-ticking chunks inside them). Light settling only
farther out, such as that of chunks just streamed in at the edge of a large
render distance, is left to the 2 ms streaming budget; nothing the tick
reads can see it. With no players registered every loaded cell ticks, and
everything is resolved as before. A LAN host still resolves everything
before ticking, for the chunks it sends.

Natural spawning waited for all light to settle (`light_settled`); with far
light now often still settling it would have stopped while travelling. It
now waits only for the light around the players
(`MobWorld::spawn_light_settled`, `World::light_settled_for_ticks`), which
is all it reads. Generation herds, which are placed in newly generated
chunks far out, still wait for all light.

### The streaming light budget

Kept at 2 ms. Mesh jobs wait while light settles so that no mesh shows
half-spread light. In the measurements below the stream phase's p99 is
0.1–2.1 ms in every build and render distance, no frame reaches 50 ms, and
nothing points at the budget or the hold. The only cost the hold has is latency: with the
pre-tick flush now leaving far light to the budget, a newly generated chunk
at the edge of a large render distance can show a few frames later than in
v0.18, when every tick frame also flushed it. The headless harness doesn't
measure that latency; the owner's play does. Nothing measured supports
changing the budget.

## Differences from Java

- **Light engine.** Java resolves light on its own thread and random-ticks
  only chunks whose light is complete. VoxelCraft resolves it on the main
  thread; the tick and growth reads are exact, as above.
- **The lightmap** stays VoxelCraft's continuous form (smooth light
  interpolated per fragment, then Java's formula), not a sampled 16 × 16
  texture, as before.
- **Entity Distance** (`entityDistanceScaling`) and Java's other graphics
  presets aren't options in VoxelCraft; the Fancy preset's values are used.
- **Not limited by Java's distances yet:** dropped items, projectiles,
  End crystals and the dragon, other players' avatars (fog only, as before).
- **Clouds** keep VoxelCraft's own pattern and the pre-OIT nearest-surface
  look ([v0.18 atmosphere](2026-11-23-v0.18-atmosphere.md#differences-from-java)).

The equivalence tests mirror the shader in Rust `f32`, so they prove the
algebra and the evaluation order, not a GPU's `pow`. Results:

- Fog: 84,672 fragments, no byte changes; the CPU's encode equals the
  mirror's `to_srgb` exactly.
- Lightmap: when the hardware interpolates four equal corner values to
  exactly that value (`v0 + w1 (v1 − v0) + w2 (v2 − v0)`), all 774,144
  fragments agree bit for bit. If it sums `v w0 + v w1 + v w2` instead, the
  old per-fragment form itself drifts by an ulp; against that, 2 of the
  774,144 fragments land one byte apart (largest linear difference 1.1 ×
  10⁻⁶), rounding ties.

## Gaps and open decisions

- **Open decision: existing options files keep Cloud Distance 128.** v0.18
  wrote its default, 128, into every options file. Java re-applies the
  Fancy preset at each start, so a Java player on the default preset sees
  64 whatever was saved; VoxelCraft has no preset and keeps the saved
  value. Players who never chose 128 therefore keep the costlier distance
  until they change it. Java-faithful default chosen: keep saved values.
  The owner may want v0.18's 128 read as "unset".
- **Open decision: gamma-space rendering.** The fog blend's six `pow`s per
  fragment remain because VoxelCraft draws to an sRGB target and Java blends
  in gamma space. Matching Java's pipeline (a non-sRGB target, colours kept
  in gamma space) would remove them and every other conversion; it is an
  architecture change for the restructuring plan, not this track.
- **The pre-tick flush at render distance 8.** At the default distances
  (render 8 = 256 blocks, simulation 10) the block-ticking area plus its
  margin reaches the streaming edge, so most far light still counts as near
  and is flushed before the tick, as in v0.18. The bound pays off from
  about render distance 10 up.
- **A growth check beside an edit inside the tick resolves the whole
  backlog.** When light work near a cell is queued during the tick (a
  fluid, a falling block), a growth check there resolves all queued light,
  including far light the pre-tick check left. v0.18 flushed that far light
  before every tick, so its backlog never built up over ticks; now it can
  grow for as long as the 2 ms streaming budget falls behind. The headless
  runs show one 31 ms random-tick step in 54 runs (p99 unchanged), which may
  be this. If the Mac shows tick spikes at large render distances, splitting
  the light queues by area is the next step.
- **Chunk appearance latency** at large render distances may rise by a few
  frames (see the streaming budget); not measured headless.
- **Generation herds** wait for all light to settle, so with far light often
  settling they may be placed a little later than in v0.18. Their positions
  and rolls are unchanged.
- **Not limited by Java's distances yet:** dropped items, projectiles, End
  crystals, the dragon and other players.
